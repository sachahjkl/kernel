# Data-Oriented Design and Cache-Conscious Patterns for Operating System Kernels

Verification legend used throughout:
- **[V]** = checked this session against the linked page (fetched, or returned in a search snippet of that page).
- **[R]** = recalled from prior knowledge of a well-known primary source; the URL is the canonical location but the exact figure was NOT re-read this session. The report writer should treat [R] numbers as "probably right, verify before quoting as exact".

## 1. Foundational DOD material: what does each resource teach?

### Takeaway
The canon agrees on one thesis: the program's job is to transform data, the dominant cost on post-2000 hardware is memory access rather than computation, so design starts from the actual data (how many, how often accessed, which fields together) and not from an object model. The practical toolkit is small and repeats across all authors: arrays over node-based structures, SoA / hot-cold splitting, indices instead of pointers, shrinking every per-element byte, batch ("where there is one, there are many"), and measure.

### Cited Findings

**Mike Acton, "Data-Oriented Design and C++" (CppCon 2014)**
- [R] Core statements: "The purpose of all programs, and all parts of those programs, is to transform data from one form to another"; "If you don't understand the data, you don't understand the problem"; "Where there is one, there are many" (design for the batch, not the single element); "the hardware is the platform, not the software"; three "lies": software is a platform, code should be designed around a model of the world, code is more important than data. Includes the worked example of a bool member in a large struct wasting most of each cache line fetched, and counting how many cache lines per frame carry useful bits (information density). — [CppCon 2014 video](https://www.youtube.com/watch?v=rX0ItVEVjHc)

**Richard Fabian, "Data-Oriented Design" (book, online 2013, print 2018)**
- [R] Frames DOD as relational-database normalization applied to in-memory data: tables (arrays) per component, existence-based ("existential") processing where membership in a table replaces boolean flags and branches, hierarchical level of detail, hot/cold splitting, and avoiding per-object virtual dispatch by sorting data by type. — [dataorienteddesign.com/dodbook](https://www.dataorienteddesign.com/dodbook/)
- [V] ECS is commonly treated as a data-oriented architectural style using SoA and archetype-based storage; critics note DOD is not synonymous with ECS, and an ECS can be implemented in a non-data-oriented way (e.g. per-element linked lists). — [Wikipedia: Entity component system](https://en.wikipedia.org/wiki/Entity_component_system); [S. Schoener, "Data Oriented Design - An Interpretation" (2019)](https://blog.s-schoener.com/2019-06-09-data-oriented-design/)

**Andrew Kelley, "A Practical Guide to Applying Data-Oriented Design" (Handmade Seattle, Nov 2021)**
- [V] Talk given at Handmade Seattle 2021; "picks up where Mike Acton left off"; covers "struct layout, data type sizing, memory alignment"; applied to the Zig compiler's tokenizer/parser/AST/ZIR. — [Handmade Seattle talk page](https://media.handmade-seattle.com/practical-data-oriented-design/); [video on Vimeo](https://vimeo.com/649009599); [D. Creager's note](https://dcreager.net/handmade/kelley-on-dod/); [lobste.rs discussion](https://lobste.rs/s/vbiu6y)
- [R] Techniques presented: (1) use 32-bit indices instead of 64-bit pointers; (2) store booleans "out of band" (membership in a separate array/set instead of a field); (3) eliminate padding with struct-of-arrays (Zig's `MultiArrayList`); (4) store sparse/rare data in side hash maps; (5) "encodings" instead of polymorphism (tag + compact payload, extra data in a side array). The talk's rule of thumb: identify where you have many objects in memory and shrink the size of each one. — [Vimeo video](https://vimeo.com/649009599)

**Ulrich Drepper, "What Every Programmer Should Know About Memory" (2007)**
- [R] 114-page paper, serialized on LWN in 2007. Explains DRAM vs SRAM, cache hierarchy, associativity, TLBs, NUMA, prefetching, false sharing, and tools. Classic table for a Pentium M: register <=1 cycle, L1d ~3 cycles, L2 ~14 cycles, main memory ~240 cycles. Shows sequential vs random list traversal across working-set sizes, where random pointer-chasing beyond L2 costs orders of magnitude more per element than sequential; recommends separating read-mostly from written data, per-CPU data, and aligning hot data to cache lines. — [PDF (akkadia.org)](https://www.akkadia.org/drepper/cpumemory.pdf); [LWN serialization, part 1](https://lwn.net/Articles/250967/)

**Scott Meyers, "CPU Caches and Why You Care" (code::dive 2014 and earlier versions)**
- [R] Demonstrates row-major vs column-major matrix traversal and a multi-threaded counting example whose scaling collapses due to false sharing on adjacent counters; guidance: linear array traversals are prefetcher-friendly, "be alert for false sharing in MT systems", and keep hot data compact. — [code::dive 2014 video](https://www.youtube.com/watch?v=WDIkqP4JbkE)

**Chandler Carruth, "Efficiency with Algorithms, Performance with Data Structures" (CppCon 2014)**
- [R] "Efficiency" comes from algorithms (doing less work); "performance" comes from data structures (doing work faster via cache locality). Calls linked lists and `std::map`/`std::unordered_map` node-based containers the wrong default; vectors and open-addressing flat tables are the right default. — [CppCon 2014 video](https://www.youtube.com/watch?v=fHNmRkzxHWs)

**Stoyan Nikolov, "OOP Is Dead, Long Live Data-Oriented Design" (CppCon 2018)**
- [R] Compares Chromium's OOP animation system with a DOD re-implementation in the Hummingbird engine; reports the DOD version several times faster (talk cites ~6x) with better scalability and testability, at the cost of less familiar code. — [CppCon 2018 video](https://www.youtube.com/watch?v=yy8jQgmhbAU)

**Jonathan Blow / Jai**
- [V] Video "Data-Oriented Demo: SOA, composition", uploaded by Blow on 21 Jan 2015, introduced an `SOA` annotation applicable to a struct declaration (making its storage SoA by default) or to an individual array, with an `AOS` counterpart; goal was data-oriented game-object systems that still allow composition via `using` without C++-style inheritance, whose differently-sized classes hinder contiguous allocation. — [fan-compiled Jai overview, SOA page](https://pixeldroid.com/jailang/overview/Features/SOA/); [D forum thread summarizing the video, 22 Jan 2015](http://forum.dlang.org/thread/ckeqxhkqjyvmqodrfhhj@forum.dlang.org)
- [V] The pitch at the time: converting between AoS and SoA requires only inserting/removing the `SOA` keyword at the struct definition; no use-site changes. — [Rust Internals "Jai language primer"](https://internals.rust-lang.org/t/jai-language-primer/3176); [HN thread](https://news.ycombinator.com/item?id=15052548)
- [V] Later history (secondhand only): a May 2020 ISO C++ std-proposals post says "more recently Jonathan seems to have foregone the SOA/AOS keywords"; a Jai-community post states SOA/AOS "was removed, as its functionality is covered by all metaprogramming stuff". No direct Blow quote or changelog entry was found. — [std-proposals, May 2020](https://lists.isocpp.org/std-proposals/2020/05/1409.php); [Jai (programming language), Wikipedia](https://en.wikipedia.org/wiki/Jai_(programming_language))
- [V] Jai began in 2014, is still closed beta, and all public documentation is fan-compiled from streams. — [Wikipedia: Jai](https://en.wikipedia.org/wiki/Jai_(programming_language))

**Casey Muratori, Performance-Aware Programming / "Clean Code, Horrible Performance" (2023)**
- [R] Course teaches reading the CPU's actual behaviour (instruction decoding, IPC, cache, SIMD, measurement). The 2023 essay/video shows that replacing a virtual-dispatch shape hierarchy with a switch gives ~1.5x, and a table-driven version ~10x or more, i.e. "clean code" rules cost the equivalent of many years of hardware progress. — [computerenhance.com: Clean Code, Horrible Performance](https://www.computerenhance.com/p/clean-code-horrible-performance); [course home](https://www.computerenhance.com/)

### Inferences
- The Jai SOA story is itself a design lesson for a kernel language/toolchain: layout transformation was first a keyword, then (reportedly) dropped in favour of compile-time metaprogramming. For a kernel, this argues for making layout (AoS/SoA/hot-cold) a generated or declarative property that is checked at build time, rather than hand-maintained. Linux arrived at a weak version of the same thing with `__cacheline_group_begin/end` build-time assertions (section 3).
- Kelley's list (indices not pointers, out-of-band flags, SoA, side tables for rare data, compact encodings) maps one-to-one onto kernel objects: PIDs/handles as indices into tables, state membership via run-queue arrays rather than flag fields, rare fields (ptrace, audit, cgroup details) in side tables.
- Acton's "where there is one, there are many" is exactly the argument behind batched kernel interfaces (io_uring, VPP, FlexSC) covered in section 3.

### Gaps
- Kelley's exact before/after numbers for the Zig compiler (token size, AST node size, wall-clock and cache-miss reductions) and his latency table could not be read: the talk is video-only and the note pages contain no figures. Do not quote specific numbers without watching the talk.
- Exact speedup figures in Nikolov's and Muratori's material are from recall; verify before quoting.
- No primary (Blow-authored) written statement on why SOA was removed from Jai was found; only secondhand community reports.
- Exact YouTube ID for Blow's 2015 demo was not verified; the fan wiki cites the title and date.

## 2. Hardware facts: what are the concrete numbers?

### Takeaway
On 2021-2024 cores an L1 hit costs 4-5 cycles (~1 ns), L2 ~2.5-5 ns, L3 ~8-15+ ns, and DRAM ~60-110 ns, so one cache miss to DRAM costs as much as roughly 200-400 simple instructions; a bare syscall round trip (~150 cycles in 2010) is cheaper than a single DRAM miss, and the dominant cost of kernel entry is the pollution it causes, not the mode switch. Cache-line size is 64 B on x86 and on most ARM, but Apple Silicon reports 128 B to software, so line size must be a build/boot parameter.

### Cited Findings

**Cache and DRAM latency**
- [V] Golden Cove (Intel, 2021+): L1D 5 cycles (Zen 4: 4 cycles); L2 load-to-use 2.94 ns at max clock, 4.68 ns at 3.2 GHz since latency is fixed in cycles; client L3 measured above 15 ns, almost 20 cycles more than Zen 3/Zen 4. — [Chips and Cheese, "Going Armchair Quarterback on Golden Cove's Caches"](https://chipsandcheese.com/p/going-armchair-quarterback-on-golden-coves-caches); [Chips and Cheese, Zen 4 part 2](https://chipsandcheese.com/p/amds-zen-4-part-2-memory-subsystem-and-conclusion)
- [V] Zen 4 (7950X, 2022): L2 2.44 ns (5950X: 2.4 ns); L3 back to the 8-9 ns range. — [Chips and Cheese, Zen 4 part 2](https://chipsandcheese.com/p/amds-zen-4-part-2-memory-subsystem-and-conclusion)
- [V] Sapphire Rapids (server Golden Cove, 2023): DRAM latency just above 107 ns measured with a 1 GB array and 2 MB pages. — [Chips and Cheese, "A Peek at Sapphire Rapids"](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids)
- [V] Apple M1 Firestorm: L1D 3 cycles for simple pointer access, L2 18 cycles, RAM latency = 18 cycles + 91 ns (about 100 ns). — [7-cpu.com Apple M1](https://www.7-cpu.com/cpu/Apple_M1.html); [HN comment](https://news.ycombinator.com/item?id=25420290)
- [V] 2010 baseline (Nehalem Core i7, FlexSC paper Table 3): 64 B lines for all caches; L1i 32 KB / 3 cycles; L1d 32 KB / 4 cycles; L2 512 KB / 11 cycles; shared L3 8 MB / 35-40 cycles; memory 250 cycles average; L1 TLB 64 data + 64 instruction entries; L2 TLB 512 entries. — [Soares & Stumm, FlexSC, OSDI 2010](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)
- [V] Classic "latency numbers every programmer should know" list (Dean/Norvig lineage; dated but widely cited): L1 reference 0.5 ns, branch mispredict 5 ns, L2 reference 7 ns, mutex lock/unlock 25 ns, main memory reference 100 ns. — [jboner gist](https://gist.github.com/jboner/2841832)
- [R] Drepper (2007, Pentium M): L1d ~3 cycles, L2 ~14 cycles, main memory ~240 cycles. — [Drepper PDF](https://www.akkadia.org/drepper/cpumemory.pdf)

**Cache line size**
- [V] macOS on M1 reports `hw.cachelinesize: 128` (and `hw.l1dcachesize: 65536` for efficiency cores in one dump); the Go `x/sys/cpu` package changed its arm64-darwin cache line pad from 64 to 128 on that basis; Apple's developer guidance (as quoted in a mimalloc PR) is to query `hw.cachelinesize` at run time rather than hard-code it. — [cpufun, "More M1 fun: Hardware Information"](https://cpufun.substack.com/p/more-m1-fun-hardware-information); [Go x/sys commit](https://go.googlesource.com/sys/+/20c2bfdbfe249b02ea905477d7cff52673dadfa2); [Go issue 53075](https://golang.org/issue/53075)
- [V] Conflict: 7-cpu lists M1 L1D as "128 KB, 64 B/line", and forum reports say `CTR_EL0`/`getconf` under Asahi Linux return 64 B, with 128 B apparently reflecting the shared L2. These are forum-level sources. — [7-cpu.com Apple M1](https://www.7-cpu.com/cpu/Apple_M1.html); [HN thread](https://hn.svelte.dev/item/45216327)

**Syscall cost and pollution (FlexSC, OSDI 2010, Nehalem, Linux)**
- [V] Direct mode-switch cost: 79 cycles to enter and 71 cycles to leave the kernel; null syscall round trip ~150 cycles, "less than the latency of a memory access that misses the processor caches (250 cycles on our machine)". — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)
- [V] Table 1, state evicted per syscall (instructions / cycles / kernel IPC / L1i lines / L1d lines / L2 / L3 / dTLB entries): `stat` 4972 / 13585 / 0.37 / 32 / 186 / 660 / 2559 / 21; `pread` 3739 / 12300 / 0.30 / 32 / 294 / 679 / 2160 / 20; `pwrite` 5689 / 31285 / 0.18 / 50 / 373 / 985 / 3160 / 44; `open+close` 6631 / 19162 / 0.34 / 47 / 240 / 900 / 3534 / 28; `mmap+munmap` 8977 / 19079 / 0.47 / 41 / 233 / 869 / 3913 / 7; `open+write+close` 9921 / 32815 / 0.30 / 78 / 481 / 1462 / 5105 / 49. — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)
- [V] With a 32 KB L1d (512 lines), these syscalls "pollute at least half of the d-cache, and almost all of the d-cache in the open+write+close case"; the 64-entry dTLB is also significantly polluted. — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)
- [V] After a `pwrite` it takes up to 14,000 cycles before Xalan's user-mode IPC recovers; Xalan's user IPC (baseline 1.46) degrades by up to 65% (to 0.50-0.58) with a `pwrite` every 1,000-2,000 instructions; SPEC JBB (baseline 0.97) degrades 45%. At typical server syscall frequencies user-mode IPC degradation is 20-60%. — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)
- [V] Kernel-mode IPC across the measured syscalls is 0.18-0.47 (average 0.32), up to 8x lower than the user-mode IPC of the same machine: kernel code itself runs cache-cold. For syscalls every <2,000 instructions the direct cost dominates; between 2,000 and 100,000 instructions the indirect (pollution) cost dominates. — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)

**KPTI / Meltdown mitigation cost (Brendan Gregg, Netflix, Feb 2018)**
- [V] Overhead ranges from 1% to over 800% depending on syscall/page-fault rate and working set size; about 2% at 50k syscalls/s per CPU; under 0.5% below 10k/s/CPU; context switches cost like syscalls (add the rates). — [Gregg, "KPTI/KAISER Meltdown Initial Performance Regressions"](https://www.brendangregg.com/blog/2018-02-09/kpti-kaiser-meltdown-performance.html)
- [V] Working sets above ~10 MB add TLB-flush overhead that can turn 1% into 7%; cache access pattern can add ~10% more (7% to 17%). PCID (Linux 4.14) brings a 2.1% case to ~0.5%; adding huge pages turned it into a 3.0% gain. — [Gregg 2018](https://www.brendangregg.com/blog/2018-02-09/kpti-kaiser-meltdown-performance.html)
- [V] PMC data at the worst-case point: nopti IPC 0.89 / dTLB walk 0.23% / iTLB 0.01%; pti without PCID IPC 0.81 / 2.91% / 2.21%; pti+PCID 0.87 / 0.22% / 0.32%; pti+PCID+THP 0.91 / 0.00% / 0.22%. Extreme case without PCID: dTLB walks 27.40% and iTLB walks 22.63% of cycles, IPC falling from 0.86 to 0.10. LLC hit ratio dropped from ~55% to ~50% at the jump, attributed to extra page-table memory. — [Gregg 2018](https://www.brendangregg.com/blog/2018-02-09/kpti-kaiser-meltdown-performance.html)
- [V] MySQL OLTP at 75k syscalls/s/CPU: measured 5% loss (8 CPUs), 3% (64 CPUs); a stress test at 210k syscalls/s/CPU + 27k context switches/s/CPU measured 25%. — [Gregg 2018](https://www.brendangregg.com/blog/2018-02-09/kpti-kaiser-meltdown-performance.html)

**Retpoline / indirect call cost**
- [V] Paolo Abeni's 2018 "net: mitigate retpoline overhead" series (indirect call wrappers, `INDIRECT_CALL_*`) compares a function pointer against known built-in targets and calls directly; it gave >10% improvement on a UDP GRO benchmark and a smaller measurable gain on TCP SYN flood; the cover letter states replacing one retpolined indirect call with several compare branches plus a direct call wins "even when multiple branches are added - 5 or more". — [LWN: net: mitigate retpoline overhead](https://lwn.net/Articles/773985/); [LKML](https://lkml.org/lkml/2018/12/5/1206)
- [V] The original retpoline LLVM review reported 5-10% overhead on well-tuned servers. — [LLVM D41723](https://reviews.llvm.org/D41723)

**Context switch and page fault**
- [V] Direct context-switch cost: roughly 1.2-1.5 us pinned to one core and ~2.2 us unpinned (Bendersky, 2018 hardware); a 2018 measurement report gives a best case of at least ~3,400 cycles; indirect cache/TLB cost can be much larger. — [E. Bendersky 2018](https://eli.thegreenplace.net/2018/measuring-context-switching-and-memory-overheads-for-linux-threads/); [arXiv 1811.01412](https://arxiv.org/pdf/1811.01412); [Li et al., "Quantifying the Cost of Context Switch" (ExpCS 2007)](https://www.usenix.org/legacy/events/expcs07/papers/2-li.pdf)
- [V] Minor page fault: ~1,000-4,000 cycles (2018 report); LMBench-based average of ~1.02 us on a vanilla kernel; major faults ~260k-560k cycles. — [arXiv 1811.01412](https://arxiv.org/pdf/1811.01412); [arXiv 2212.12671](https://arxiv.org/pdf/2212.12671)

**False sharing / coherence traffic**
- [V] The multikernel paper's shared-memory experiment (4x4-core AMD) has every core update the same cache lines and plots latency in cycles growing with core count, versus message-passing variants; its reader-writer-lock example notes the lock's line "ping-pongs between the readers' caches". — [Baumann et al., SOSP 2009 slides](https://www.cs.ucr.edu/~nael/cs202/lectures/baumann-slides-sosp09.pdf); [paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/baumann09multikernel.pdf)
- [V] The scalable-commutativity work defines "conflict-free" at exactly cache-line granularity: no core writes a cache line that another core reads or writes. — [Clements et al., SOSP 2013](https://www.read.seas.harvard.edu/~kohler/pubs/clements13scalable.pdf)

### Inferences
- Ratio that should drive design: DRAM miss (~100 ns) vs L1 hit (~1 ns) is ~100x; vs a null syscall (2010: 150 cycles, ~50 ns) the miss is more expensive. A kernel path that takes 5 dependent DRAM misses (pointer chase through 5 cold objects) costs ~0.5 us regardless of how few instructions it executes. Counting cache lines touched per operation is therefore the right primary metric, as seL4/L4 and the Linux networking team both ended up doing.
- FlexSC Table 1 implies the kernel's own footprint is the problem: a single `pwrite` touches 373 L1d lines (~24 KB) and runs at IPC 0.18. A data-oriented kernel should target a per-syscall data footprint budget in lines, the way L4 budgets IPC.
- Because Apple reports 128 B and x86 uses 64 B (and some POWER/s390 use 128/256 B), cache-line size should be a compile-time parameter and layouts should be expressed as "groups that must fit in N bytes", which is exactly what Linux's v5 revision of the cache-group series changed to (section 3).
- KPTI data shows TLB reach and page-table memory are part of the same budget: PCID/ASID use and huge-page mapping of kernel data are not optional extras for a design centred on the memory wall.

### Gaps
- No single authoritative 2025-2026 table of L1/L2/L3/DRAM latencies across current cores (Zen 5, Lion Cove, Apple M4, Graviton 4) was found; numbers above are 2021-2023 parts.
- No reliable, recent primary measurement of IPI cost or of bare `getpid`-style syscall latency (with current mitigations) was found this session. Order-of-magnitude figures circulate (syscall ~50-100+ ns with mitigations; IPI on the order of 1-2 us round trip) but are unsourced here.
- TLB reach on current cores (entries x page size; e.g. L2 TLB sizes of 1.5k-3k entries giving only 6-12 MB reach with 4 KB pages) was not verified against a primary source this session.
- Hardware prefetcher behaviour (stride/stream detection limits, the 4 KB page-boundary limit for L1/L2 prefetchers) was not sourced this session; Drepper section 6 covers it for 2007-era hardware.
- NUMA remote-access latency numbers were not sourced.
- Whether Apple L1 lines are physically 64 B or 128 B remains unresolved between sources.

## 3. Kernel-side evidence: where were kernels designed or re-engineered around cache lines, batching, SoA, per-CPU data, or less pointer chasing?

### Takeaway
Every high-performance kernel path that has been seriously measured converged on the same handful of DOD moves: count cache lines on the fast path and regroup fields (L4/seL4 IPC, Linux dentry, Google's net structs), partition state per CPU so no line is shared (Linux per-CPU/SLUB/RCU, DragonFly, Barrelfish, sv6), replace pointer-linked structures with wide array-like nodes (maple tree, XArray, RadixVM), and batch across the user/kernel or layer boundary (FlexSC, io_uring, VPP, XDP). All were retrofits or special paths; none applied the principle to the whole kernel object model.

### Cited Findings

**Linux: struct layout and cache-line grouping**
- [V] Google's "Analyze and Reorganize core Networking Structs to optimize cacheline consumption" (Coco Li, with Eric Dumazet; v1 mid-2023, v8 Nov 2023, merged by David Miller as `net-cacheline-optimizations`) states that variable-heavy networking structs were organized "chronologically, logically and sometimes by cacheline access", and regroups fast-path fields of `netns_ipv4`, `net_device`, `tcp_sock` (plus SNMP counters) by access pattern. — [LWN: cover letter v7](https://lwn.net/Articles/951321); [LWN: earlier posting](https://lwn.net/Articles/948950/); [merge commit](https://lab.nexedi.com/kirr/linux/-/commit/8470e4368b0f3ba788814f3b3c1142ce51d87e21?expanded=1)
- [V] Documented footprint: `tcp_sock` spans 42 cache lines (2664 bytes), with 12 fast-path lines / 396 fast-path bytes reducible to 8 lines; `net_device` spans 39 lines (2240 bytes), 12 fast-path lines / 234 fast-path bytes reducible to 4. — [commit "Documentations: Analyze heavily used Networking related structs"](https://kernel.googlesource.com/pub/scm/linux/kernel/git/netdev/net-next/+/14006f1d8fa24a2320781ad503ca1cba92e940d2)
- [V] Measured result (neper `tcp_rr`, threads = CPUs, kernel 6.5-rc1; metric = CPU-seconds per round trip, lower is better). AMD (100 Gb/s NIC, 256 MB L3): IPv4 -36.65% (30k flows), -41.62% (20k), -44.47% (10k), -44.00% (5k), -35.43% (1k); IPv6 -38.16%, -40.77%, -44.20%, -41.72%, -20.48%. Intel (200 Gb/s NIC, 105 MB L3), IPv6: -1.16% (30k), -4.88% (20k), -4.76% (10k), -5.24% (5k), +3.31% (1k, a slight regression). — [LWN 951321](https://lwn.net/Articles/951321)
- [V] The series adds `__cacheline_group_begin/end` markers plus build-time assertions in `include/linux/cache.h` ("cache: enforce cache groups"); v5 changed the group-size requirement from a cache-line count to the sum of member sizes so as not to assume a line size. It also adds `Documentation/networking/net_cachelines/` recording which fields are fast-path, and asks developers to update it when adding fields. A follow-up series added the markers to `net_device` and `tcp_sock`. — [LWN 951321](https://lwn.net/Articles/951321); [follow-up merge](https://mirrors.lzu.edu.cn/git/linux-nf/-/commit/faf4cf7495431d396147d5c73a84ccfddc458c9d); [v4 thread](https://lore.kernel.org/all/20231026081959.3477034-1-lixiaoyan@google.com/T/)
- [V] dcache: Nick Piggin's 2011 commit "fs: cache optimise dentry and inode for rcu-walk" moved hot fields to the front of `struct dentry` so an RCU path-walk step touches only the first 56 bytes of the dentry, and rearranged the inode so RCU lookup touches a single cache line in the inode plus one in `i_op`. RCU-walk performs lookup of intermediate components "without any stores to shared data in the dentry or inode". — [commit 44a7d7a878c9](https://git.zx2c4.com/linux-dev/commit/?id=44a7d7a878c9cbb74f236ea755b25b6b2e26a9a9); [kernel docs: Pathname lookup](https://www.kernel.org/doc/html/latest/filesystems/path-lookup.html); [LWN: Dcache scalability and RCU-walk](https://lwn.net/Articles/419811/); [LWN: RCU-walk](https://lwn.net/Articles/649729/)
- [V] In 2012 Linus Torvalds prototyped a small direct-mapped "L1" cache (`dcache_l1` array, `d_lookup_l1()`) in front of the dentry hash chains to avoid walking the hash list. — [LWN: Linus Torvalds's dcache patch](https://lwn.net/Articles/510313/)
- [R] Tooling: `pahole` (dwarves) prints struct layout with holes, padding and cache-line boundaries and can propose reorderings; kernel annotations `____cacheline_aligned(_in_smp)`, `__read_mostly`, `__randomize_layout`. — [LWN: Poke-a-hole and friends](https://lwn.net/Articles/335942/); [include/linux/cache.h](https://elixir.bootlin.com/linux/latest/source/include/linux/cache.h)

**Linux: struct page, folios, memdescs**
- [V] Long-term goal of the folio project ("New York interpretation"): shrink `struct page` to a single 64-bit memory descriptor (`memdesc`) whose low 4 bits give a type (buddy, file folio, anon folio, KSM, slab, page table `ptdesc`, per-CPU, zpdesc, etc.) and whose remaining bits point to a separately allocated descriptor from 16-byte-aligned TYPESAFE_BY_RCU slabs; a folio is 80 bytes, about 51 per 4 KiB page. — [kernelnewbies: MatthewWilcox/Memdescs](https://kernelnewbies.org/MatthewWilcox/Memdescs); [Memdescs/Path](https://kernelnewbies.org/MatthewWilcox/Memdescs/Path)
- [V] Status at LSFMM+BPF 2025: the single-u64 goal "will not be achieved this year"; 2025 goals were making `struct folio` independently allocatable, removing `mapping`/`index`/`lru` references from `struct page`, splitting out the networking page pool and slab descriptors; "exactly one" page flag bit remained free; large-folio creation in `generic_perform_write()` can "double write performance in some tests". Although `struct folio` grows, "there will be a lot fewer of them, so the overall memory-management overhead will decrease". The plan page lists a 16-byte `struct page` step targeted for 2026; an Oct 2025 RFC separated `ptdesc` from `struct page`. — [LWN, LSFMM 2025 folio update](https://lwn.net/Articles/1015320); [LWN, LSFMM 2024](https://lwn.net/Articles/973565); [LWN 1042701](https://lwn.net/Articles/1042701/); [State of the Page, Jan 2025](https://lkml.iu.edu/hypermail/linux/kernel/2501.1/01442.html)
- [R] Baseline: `struct page` is 64 bytes per 4 KiB page (one cache line; ~1.6% of RAM). — [LWN: Clarifying memory management with page folios](https://lwn.net/Articles/849538/)

**Linux: data structures replacing pointer-heavy ones**
- [V] Maple tree (Liam Howlett, Matthew Wilcox; merged in 6.1) is "an RCU-safe range based B-tree designed to use modern processor cache efficiently", replacing the VMA red-black tree plus the VMA doubly linked list (plus the vmacache); higher branching factor gives a much shorter tree than an rbtree's factor of 2. — [LWN: Introducing maple trees](https://lwn.net/Articles/845507); [Oracle blog: The Maple Tree](https://blogs.oracle.com/linux/the-maple-tree); [v8 patch series](https://lkml.iu.edu/2204.3/03633.html)
- [V] Node size: the Oracle blog (early design) says maple nodes are "only 2 cache lines, which is 50% smaller than the rbtree 3 cache lines"; [R] the merged implementation uses 256-byte nodes on 64-bit (16 slots for range nodes, 10 for allocation-range nodes, up to 31 for dense nodes). The two figures conflict because the design changed. — [Oracle blog](https://blogs.oracle.com/linux/the-maple-tree); [kernel docs: Maple Tree](https://docs.kernel.org/core-api/maple_tree.html)
- [R] XArray (Wilcox, 4.20) replaced the radix-tree API for the page cache: a 64-slot-per-node radix structure indexed by integer, presenting as an "automatically resizing array". — [LWN: The XArray data structure](https://lwn.net/Articles/745073/); [kernel docs: XArray](https://docs.kernel.org/core-api/xarray.html)

**Linux: per-CPU data, RCU, allocators**
- [R] Per-CPU variables and `this_cpu_*` operations compile to a single segment-relative instruction on x86, avoiding both locks and shared lines. — [kernel docs: this_cpu operations](https://www.kernel.org/doc/html/latest/core-api/this_cpu_ops.html)
- [R] SLUB keeps a per-CPU active slab with a lockless freelist fast path; SLAB earlier used per-CPU array caches (LIFO arrays of object pointers, so recently freed, cache-hot objects are reused first), an idea from Bonwick's magazines. — [LWN: The SLUB allocator](https://lwn.net/Articles/229984/); [Bonwick & Adams, "Magazines and Vmem", USENIX ATC 2001](https://www.usenix.org/legacy/event/usenix01/bonwick.html)
- [V] MOSBENCH study (Boyd-Wickizer et al., OSDI 2010): seven applications on a 48-core machine; all except gmake hit kernel scalability bottlenecks; fixed with 3002 lines of changes using standard techniques plus "sloppy counters" (per-core reference-count caches) for dentries, mount points, routing entries and protocol memory accounting; per-core accept backlog queues for Apache. Conclusion: "no scalability reason to give up on traditional operating system organizations just yet". — [paper (MIT DSpace)](https://dspace.mit.edu/handle/1721.1/62203); [MOSBENCH page](https://pdos.csail.mit.edu/archive/mosbench); [summary](https://highscalability.com/paper-an-analysis-of-linux-scalability-to-many-cores/)
- [R] The same paper lists false sharing fixes: read-mostly fields of `net_device` and `device` shared lines with frequently written fields and were moved to separate cache lines. — [paper PDF](https://pdos.csail.mit.edu/papers/linux:osdi10.pdf)

**Batching across the user/kernel boundary**
- [V] FlexSC (Soares & Stumm, OSDI 2010): "exception-less" syscalls posted to shared syscall pages whose entries are sized to exactly 64 bytes ("64 is a divisor of popular cache line sizes"), executed in batches by kernel syscall threads, optionally on another core; improves Apache by up to 116%, MySQL by up to 40%, BIND by up to 105% with no application changes (via the M-on-N FlexSC-Threads library). On Apache, user-mode and kernel-mode IPC both improve; kernel IPC improves 36% single-core and 25% on four cores. — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf); [OSDI slides](https://static.usenix.org/events/osdi10/tech/slides/soares.pdf)
- [V] Caveat from the Q&A: the authors had not measured cache contention caused by user-level rescheduling. — [;login: OSDI'10 reports](https://www.usenix.net/system/files/login/articles/105438-OSDI10reports.pdf)
- [V] io_uring (Jens Axboe, Linux 5.1, 2019): application and kernel communicate through two shared ring buffers, a submission queue and a completion queue, with two new syscalls (`io_uring_setup`, `io_uring_enter`); polled modes can perform I/O without any syscall. A later batching patch reports ~6.6M IOPS random read at depth 128 on two Optane gen2 drives. — [LWN: Ringing in a new asynchronous I/O API](https://lwn.net/Articles/776703/); [Phoronix](https://www.phoronix.com/news/Linux-io_uring-Fast-Efficient); [Kernel Recipes 2019 slides](https://archives.kernel-recipes.org/wp-content/uploads/2025/01/kernel-recipes-2019-axboe.pdf)
- [R] Axboe's design paper explains the ring layout (SQ is an index array into an SQE array so entries can be prepared out of order; 64-byte SQEs, 16-byte CQEs), memory-barrier-only coordination, registered buffers/files to avoid per-call refcounting, and `IORING_SETUP_SQPOLL` kernel-side polling. — [Axboe, "Efficient IO with io_uring" (2019)](https://kernel.dk/io_uring.pdf)

**Vector / batch packet processing**
- [V] VPP (fd.io): scalar per-packet processing thrashes the instruction cache when the code path exceeds the L1 I-cache and its deep call stack pressures the D-cache; VPP pulls vectors of up to 256 packets from RX rings and runs the whole vector through one graph node at a time, so "the first packet warms the I-cache" for the rest; stack depth is limited to a few frames; nodes pipeline and prefetch to hide dependent-read latency; vector size adapts to load, making the system more efficient as load rises. — [fd.io: Scalar vs Vector packet processing](https://s3-docs.fd.io/vpp/25.10/aboutvpp/scalar-vs-vector-packet-processing.html); [fd.io: What is vector packet processing](https://fdio-vpp.readthedocs.io/en/latest/overview/whatisvpp/what-is-vector-packet-processing.html)
- [V] A 2017 DPDK-summit VPP test reported average vector size ~24-27 with a max of 255. — [DPDK Summit 2017 VPP slides](https://fast.dpdk.org/events/slides/DPDK-2017-04-VPP.pdf)
- [R] netmap (Rizzo, USENIX ATC 2012) removed per-packet `sk_buff` allocation and syscalls with preallocated shared rings and batching; reported 14.88 Mpps (10 GbE line rate) on one core at 900 MHz. — [netmap paper](https://www.usenix.org/conference/atc12/technical-sessions/presentation/rizzo)
- [R] XDP (Hoiland-Jorgensen et al., CoNEXT 2018) runs eBPF at the driver before `sk_buff` allocation; reported ~24 Mpps per core for drop. — [XDP paper](https://dl.acm.org/doi/10.1145/3281411.3281443)

**Microkernel IPC as cache-footprint engineering**
- [V] Liedtke, "Improving IPC by Kernel Design" (SOSP 1993): on a 486-DX50 with an 8 KB on-chip cache, L3 IPC was 22x faster than Mach for 8-byte messages down to 3x for 4 KB messages; individual optimizations were accounted in cycles (e.g. ~100 cycles saved per IPC by minimizing TLB misses). — [paper (Waterloo mirror)](https://rcs.uwaterloo.ca/papers/l4.pdf)
- [V] Liedtke's "On µ-kernel Construction" (SOSP 1995) line of argument, as summarized: most cache misses occurred in the kernel, and Mach's slowness came from a "substantially higher cache-miss rate" due to its large footprint, not from the microkernel structure; hence the principle that the performance-critical kernel code and data must fit in the first-level cache. — [L4 microkernel family, Wikipedia](https://en.wikipedia.org/wiki/L4_microkernel_family); [paper (ACM)](https://dl.acm.org/doi/10.1145/224056.224075); [TU Dresden reading group slides on IPC performance](https://os.inf.tu-dresden.de/Studium/ReadingGroupArchive/slides/2009/20091014-IPCPerformance.pdf)
- [V] "From L3 to seL4" (Elphinstone & Heiser, SOSP 2013): the L4 design goal was minimizing cache footprint and TLB misses; one-way IPC cost is 301 cycles for seL4 on a Haswell Core i7 and 188 cycles on ARM11; the original per-thread kernel stack/TCB layout had a large cache footprint and later kernels moved to a single kernel stack; fastpath = prologue checks, capability lookup, direct process switch without invoking the scheduler. — [paper](https://www.cs.yale.edu/flint/cs428/doc/L3toseL4.pdf); [slides](https://www.trustworthy.systems/publications/nicta_slides/6930.pdf); [UNSW COMP9242 lecture](https://cgi.cse.unsw.edu.au/~cs9242/23/lectures/05a-uk.pdf)
- [V] Independent EuroSys 2019 measurement on Skylake i7-6700K: seL4 round-trip IPC 396 cycles vs 2,717 for Fiasco.OC and 8,157 for Zircon. — [cited in UNSW lecture material](https://cgi.cse.unsw.edu.au/~cs9242/22/lectures/07a-uk.pdf)

**Share-nothing / per-core kernels**
- [V] Barrelfish multikernel (Baumann et al., SOSP 2009): treats the machine as a network of cores that communicate by explicit messages and replicate state instead of sharing kernel data structures; compares TLB-shootdown (unmap) across Windows, Linux and Barrelfish; "even on present-day machines, the performance of a multikernel is comparable with a conventional OS". — [paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/baumann09multikernel.pdf); [retrospective blog](https://khale.github.io/mem-systems-w25/blog/barrelfish)
- [V] sv6 / scalable commutativity rule (Clements et al., SOSP 2013): "whenever interface operations commute, they can be implemented in a way that scales"; the Commuter tool generated 13,664 tests over 18 POSIX calls; Linux was conflict-free for 68%, sv6 for 99%, translating to linear scaling on an 80-core x86 machine. — [paper](https://www.read.seas.harvard.edu/~kohler/pubs/clements13scalable.pdf); [Commuter page](https://pdos.csail.mit.edu/archive/commuter)
- [V] RadixVM (Clements, Kaashoek, Zeldovich, EuroSys 2013): a radix tree for mapped regions, a scalable reference-counting scheme (Refcache), and per-core page tables to avoid unnecessary TLB shootdowns; non-overlapping `mmap`/`munmap`/page faults scale perfectly on 80 cores with "no cache coherence traffic". — [paper](https://pdos.csail.mit.edu/6.828/2014/readings/radixvm.pdf)
- [R] Corey (Boyd-Wickizer et al., OSDI 2008): "applications should control sharing"; kernel data is per-core by default with explicit shares, address ranges and kernel cores. — [paper](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/boyd-wickizer/boyd_wickizer.pdf)
- [R] DragonFlyBSD LWKT: each CPU has its own scheduler and run queue; threads are not migrated preemptively; cross-CPU operations are sent as asynchronous IPI messages to the owning CPU rather than taking locks on shared structures; per-CPU slab caches follow the same pattern. — [DragonFly BSD, Wikipedia](https://en.wikipedia.org/wiki/DragonFly_BSD); [dragonflybsd.org docs](https://www.dragonflybsd.org/docs/)

**Windows NT**
- [R] Per-processor state lives in the KPCR/KPRCB (including per-processor lookaside lists and DPC queues); lookaside lists are fixed-size free lists (per-processor and system-wide) that avoid the general pool allocator; I/O completion ports batch completions and wake threads in LIFO order to keep caches warm; Windows 11 added I/O rings modelled on io_uring. — [MS Learn: Using lookaside lists](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/using-lookaside-lists); [MS Learn: I/O completion ports](https://learn.microsoft.com/en-us/windows/win32/fileio/i-o-completion-ports); [MS Learn: ioringapi](https://learn.microsoft.com/en-us/windows/win32/api/ioringapi/)

**sched_ext and BPF arenas**
- [V] BPF arenas are memory regions where the verifier relaxes pointer checking so programs can build arbitrary data structures; sched_ext schedulers currently split data into an arena part (convenient) and a BPF-map part (holding references to kernel objects). 2026 patch sets add direct kernel-side access to arena memory and a per-scheduler sub-allocator over kernel-claimed arena pages; an LPC 2025 talk (Emil Tsalapatis) covered arena-based task queues and topology representation that evolve "without kernel modifications". — [LWN 1019885](https://lwn.net/Articles/1019885); [LWN 1073891](https://lwn.net/Articles/1073891/); [LKML patch, May 2026](https://lkml.iu.edu/2605.2/09767.html); [LPC 2025 session](https://lpc.events/event/19/contributions/2036/)

**Stanford Cache Kernel (clarification)**
- [R] Cheriton & Duda's "A Caching Model of Operating System Kernel Functionality" (OSDI 1994) uses "cache" in a different sense: the supervisor-mode kernel is a fixed-size cache of OS objects (threads, address spaces, mappings) loaded and unloaded by user-level application kernels. It is not a CPU-cache-conscious design, though its fixed-size object tables are structurally table-like. — [OSDI '94 paper page](https://www.usenix.org/conference/osdi-94/caching-model-operating-system-kernel-functionality)

### Inferences
- The AMD vs Intel split in Google's results (roughly -40% vs -5% CPU per transaction from field reordering alone) shows layout sensitivity depends on the cache hierarchy; a design that budgets lines explicitly is more portable than one tuned by benchmark on one vendor.
- Linux's memdesc plan is, in DOD terms, converting a fat per-page AoS record into a dense 8-byte-per-page "type + index/pointer" column with out-of-line typed tables: the same move Kelley describes (compact tag + side tables). A new kernel can start there instead of spending a decade migrating.
- The maple tree, XArray and RadixVM all replaced binary pointer trees with wide nodes sized in cache lines; a new kernel should treat B-tree/radix nodes of 1-4 lines and flat arrays as the only default containers.
- FlexSC's 64-byte syscall entry and io_uring's 64-byte SQE are the same idea a decade apart: the syscall ABI itself is an array of cache-line-sized records. A DOD kernel could make that the only syscall mechanism.
- L4/seL4 show that a cache-line budget is enforceable as a design discipline for one path (IPC); nobody has reported doing it for every kernel path.
- sched_ext with BPF arenas is evidence that scheduler data layout can be made a replaceable policy; it does not itself impose DOD layouts.

### Gaps
- `sk_buff` and `task_struct`: no primary source with cache-line counts or a reorganization series was retrieved this session (the Google series explicitly covered `net_device`, `tcp_sock`, `netns_ipv4`, SNMP counters; `sk_buff` layout work exists historically but was not sourced here).
- seL4 fastpath footprint in cache lines: not found as a published number; only cycle counts were confirmed.
- Barrelfish's concrete TLB-shootdown and message-cost cycle numbers were not extracted.
- The lore.kernel.org thread for the Google series returned HTTP 403; reviewer objections were not read.
- io_uring paper numbers and SQPOLL results, netmap/XDP packet rates, DragonFly LWKT details, and Windows KPRCB/IRP details are from recall, not re-verified. No source was found analysing the Windows IRP (a large, heap-allocated, per-request object with a stack-location array) from a cache-footprint standpoint.
- IX, Arrakis, Shinjuku, Demikernel (dataplane OSes with run-to-completion and adaptive batching) and single-address-space systems (Opal, Mungi, Singularity) were in scope but not researched this session.
- Huge-page/TLB-oriented kernel work beyond Gregg's KPTI data (e.g. direct-map fragmentation, kernel text on 2 MB pages) was not sourced.

## 4. What are the known DOD anti-patterns in existing kernels?

### Takeaway
The documented pain points are exactly what DOD predicts: large structs laid out historically with hot and cold fields interleaved, node-based containers (rbtree plus linked list) for hot lookups, per-object reference counts and locks that turn reads into writes on shared lines, indirect calls through ops tables (made worse by retpolines), and synchronous one-at-a-time syscalls whose footprint evicts the application's cache state.

### Cited Findings
- [V] Giant structs with historically-ordered fields: Google's own characterization of core networking structs is that they were organized "chronologically, logically and sometimes by cacheline access"; `tcp_sock` 2664 bytes / 42 lines with fast-path fields scattered over 12 lines, `net_device` 2240 bytes / 39 lines with fast-path fields over 12 lines. Reordering alone reduced CPU per transaction by up to 44% on AMD. — [LWN 951321](https://lwn.net/Articles/951321); [net_cachelines commit](https://kernel.googlesource.com/pub/scm/linux/kernel/git/netdev/net-next/+/14006f1d8fa24a2320781ad503ca1cba92e940d2)
- [V] One overloaded per-page record: `struct page` serves buddy, slab, page-table, file, anon, network pool and other users through unions; the multi-year folio/memdesc project exists to split it into typed descriptors, and by 2025 only one free page-flag bit remained. — [kernelnewbies Memdescs](https://kernelnewbies.org/MatthewWilcox/Memdescs); [LWN 1015320](https://lwn.net/Articles/1015320)
- [V] Binary tree plus linked list for a hot lookup: VMAs were kept in an rbtree and a doubly linked list (and a per-thread cache to paper over it); the maple tree replaced all of them specifically "to use modern processor cache efficiently". — [LWN 845507](https://lwn.net/Articles/845507); [Oracle blog](https://blogs.oracle.com/linux/the-maple-tree)
- [V] Pointer-chasing path lookup: each path component is a hash-chain walk to a dentry, then to its inode and ops table; the mitigation was packing lookup fields into the dentry's first 56 bytes, one line in the inode plus one in `i_op`, and Linus's experimental direct-mapped front cache to skip hash-chain walking. — [commit 44a7d7a878c9](https://git.zx2c4.com/linux-dev/commit/?id=44a7d7a878c9cbb74f236ea755b25b6b2e26a9a9); [LWN 510313](https://lwn.net/Articles/510313/)
- [V] Reads that write: per-object reference counts (dentry, mount, route entries) and shared counters were the main 48-core bottlenecks in MOSBENCH; RCU-walk's whole point is path lookup with no stores to shared data. — [MOSBENCH summary](https://highscalability.com/paper-an-analysis-of-linux-scalability-to-many-cores/); [kernel docs: path-lookup](https://www.kernel.org/doc/html/latest/filesystems/path-lookup.html)
- [V] Indirect calls through ops tables: with retpolines each indirect call became expensive enough that networking added `INDIRECT_CALL_*` wrappers (compare against the likely built-in target, then call directly), for >10% on UDP GRO; the technique wins even with 5 or more added compare branches. Later work extended it to VLAN and bridging GRO paths (5.13). — [LWN 773985](https://lwn.net/Articles/773985/); [Phoronix on 5.13](https://www.phoronix.com/news/Linux-5.13-Net-Retpolines)
- [V] Scalar per-item processing through deep layered call stacks: VPP's documentation identifies I-cache thrashing when the per-packet code path exceeds L1i and D-cache pressure from deep stacks as the core inefficiency of scalar packet processing. — [fd.io docs](https://s3-docs.fd.io/vpp/25.10/aboutvpp/scalar-vs-vector-packet-processing.html)
- [V] Synchronous syscalls: a single `pwrite` evicts 373 L1d lines and 44 dTLB entries and the kernel runs at IPC 0.18-0.47; the user program needs up to 14,000 cycles to recover its IPC. — [FlexSC paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf)
- [V] Shared-memory kernel data structures as the default: the multikernel paper argues the default should be inverted (replicate and message) because shared lines ping-pong; the commutativity work found 32% of Linux's tested commutative POSIX call pairs were not conflict-free. — [multikernel paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/baumann09multikernel.pdf); [SCR paper](https://www.read.seas.harvard.edu/~kohler/pubs/clements13scalable.pdf)
- [V] Per-thread kernel stacks/TCBs in early L4 gave a large IPC cache footprint; later L4 kernels moved to a single kernel stack. — [From L3 to seL4 slides](https://www.trustworthy.systems/publications/nicta_slides/6930.pdf)

### Inferences
- Intrusive `list_head`/`hlist` linkage is pervasive in Linux and each traversal step is a dependent load into a different object; every replacement that was measured (VMA list to maple tree, pagevec/folio batches, per-CPU arrays in slab) moved toward arrays. This is an inference from the listed cases: no source retrieved this session states "linked lists are an anti-pattern in the kernel" as a general finding with numbers.
- Layout maintained by convention decays: Google had to add build-time group assertions and a documentation directory because nothing else stops a new field from splitting a hot group. A new kernel should make hot/cold grouping a checked, declarative property from day one.
- Kernel structure-layout randomization (`__randomize_layout`) and ABI/kABI stability constraints directly conflict with cache-line tuning; a new kernel with no ABI promise for internal structs avoids this.
- The POSIX interface itself forces some anti-patterns (lowest-FD allocation, shared file offsets, `fork`), per the commutativity work; a DOD kernel benefits from a non-POSIX native interface with batch-first calls.

### Gaps
- No quantitative study of how much Linux kernel time is lost to linked-list traversal specifically was found.
- No source measuring the fraction of kernel cache misses attributable to VFS dentry/inode walks on current kernels was found.
- No published `pahole`-based survey of hot/cold mixing across the whole Linux kernel (beyond networking) was found.
- `task_struct` hot/cold layout history was searched but nothing was retrieved.

## 5. Are there research or hobby kernels explicitly advertised as data-oriented, ECS-based, or batch/array-oriented, and what did they find?

### Takeaway
Essentially none of substance were found. One journal paper describes a small x86 teaching-scale kernel labelled "data-oriented", with no performance results located; the nearest serious relatives are systems that are batch- or table-oriented without using the DOD label (FlexSC, VPP, io_uring, multikernels, and reportedly DBOS). This appears to be open territory.

### Cited Findings
- [V] A paper in *Intelligent Automation & Soft Computing* (vol. 39, no. 4) describes a simplified x86 kernel built around data-oriented design aimed at big-data/cloud workloads; the prototype is a BIOS bootloader into 32-bit protected mode, text terminal, 4 GB paging, 4096-byte heap blocks, and an ATA disk driver. Only the search summary was seen; no benchmark results were retrieved. — [IASC v39 n4 article](https://www.techscience.com/iasc/v39n4/57824)
- [V] An extended web search for hobby or research OS kernels advertised as ECS-based or data-oriented returned only game-engine ECS material; "micro-kernel" in those articles refers to engine scheduling layers, not OS kernels. — [Wikipedia: Entity component system](https://en.wikipedia.org/wiki/Entity_component_system); [HN: Databases are the endgame for data-oriented design](https://news.ycombinator.com/item?id=38545417)
- [V] Systems that are batch/array-oriented in substance without the label: FlexSC (arrays of 64-byte syscall entries, batch execution; up to 116% Apache gain), VPP (vectors of up to 256 packets per graph node), io_uring (shared SQ/CQ rings). — [FlexSC](https://www.read.seas.harvard.edu/~kohler/class/aosref/soares10flexsc.pdf); [fd.io](https://s3-docs.fd.io/vpp/25.10/aboutvpp/scalar-vs-vector-packet-processing.html); [LWN 776703](https://lwn.net/Articles/776703/)
- [R] DBOS (MIT/Stanford, "DBOS: A DBMS-oriented Operating System", VLDB 2022) proposes keeping all OS state (tasks, files, messages) in tables of a distributed in-memory DBMS and expressing OS services as transactions: the closest research analogue to "table-based process tables", though aimed at cluster-level manageability rather than cache-line efficiency. — [VLDB paper](https://www.vldb.org/pvldb/vol15/p21-skiadopoulos.pdf)

### Inferences
- The absence of a credible DOD-first kernel means there are no negative results to learn from either; the risk areas must be inferred from adjacent systems: (1) FlexSC-style batching trades latency for throughput and needs a threading model that hides it; (2) share-nothing designs (Barrelfish) pay message costs for inherently shared operations; (3) SoA complicates per-object lifetime, RCU-style reclamation and capability/permission checks that naturally want "the object" in one place.
- MOSBENCH's conclusion (traditional kernels can be fixed incrementally) and Google's 2023 results (large gains from mere field reordering) together suggest much of the benefit is available without exotic architecture, provided layout is a first-class, enforced concern. A new kernel's distinctive contribution would be making that systematic: line budgets per path, generated layouts, index-addressed tables, batch-first ABI.
- Fabian's "DOD is relational normalization" and DBOS's "OS state in tables" point at the same design: kernel state as typed columns addressed by dense integer IDs (handles/PIDs as indices with generation counters), which is also how ECS engines avoid dangling pointers.

### Gaps
- No evidence was found of any Jonathan Blow statement about operating-system kernel design in this research slice (his OS-related remarks may be covered by another researcher).
- GitHub and OSDev-forum searches for hobby kernels with SoA process tables or ECS structure were not performed directly; the web search may under-represent small projects.
- The IASC paper's actual title, authors, year and results were not confirmed by reading the paper.
- DBOS details are from recall and its relevance to single-machine cache behaviour is unestablished.
