# First milestone

Status: implemented on 2026-11-10. `nix flake check` passes.

This document describes what the code does now.
It lists the choices that were made during the implementation and that the owner has not reviewed.
It lists the gaps between the code and the documents.
`GLOSSARY.md` defines the terms.

## The path from power to desktop

1. The firmware starts the boot program (`boot/`), a PE file.
2. The boot program reads the kernel module and the boot image from the boot volume. It loads the kernel with the code of `contract/module/`. It collects the memory map and the framebuffer in a `Boot_Info` record, leaves the firmware, and jumps to the kernel.
3. The kernel (`kernel/`) takes the memory, builds its tables, sets the processor tables, the interrupt controller and the timer. It reads the list of the processors in the ACPI tables and starts each one.
4. The kernel loads one program from the boot image: the root service. It gives it three handles: the machine, the framebuffer, the boot image.
5. The root service (`programs/root`) loads the other programs in user space with `system.program_start`. It starts the input service, the compositor and the console.
   The boot display (`support/bootscreen/`) is on the screen from step 2 to step 5. The boot program draws it with what it knows. The root service draws it again before each start, with the records of the kernel. The compositor then takes the screen.
6. From this point, the kernel only executes kernel operations, schedules, and turns interrupts into wakes.

## Kernel

| Subject | Now |
|---|---|
| Entry | One entry point: the `syscall` instruction. `rdi` is 0, a deadline in milliseconds, or `WAIT_FOREVER`. `rax` returns the time |
| Kernel operations | 26 command kinds in the kernel ring of each thread. `contract/operation/operation.odin` is the full list |
| Objects | Memory, Program, Thread, Interrupt, Ports, Machine, Budget, Log |
| Budget | A budget holds pages, programs and threads. `Memory_Create`, `Program_Create` and `Thread_Create` take a budget handle with the right Spend. The budget pays for memory objects, thread areas, page tables and slots. `Budget_Create` moves a part of a budget to a new budget. What an object used returns to the budget that paid. A budget with no handle ends: what it holds returns to its parent, and its parent pays for its objects. The kernel creates one budget at boot, for the root service: all the free pages and all the slots. The sum of the pages of all budgets is always the count of free pages; `System_Report` gives both numbers |
| Log | `Log` takes a Log handle with the right Write. The root service gives it to each program that it starts |
| Rights | Each handle slot holds a set of rights: Give, Read, Write, Execute, Control, Inspect, Devices, Stop. The handle of a new object has each right of its kind. `Handle_Give(target, handle, Rights)` copies a handle with the rights that are in both sets. No operation adds a right. An operation on a handle without the needed right gives `No_Right` |
| Tables | Flat and fixed: 2048 memory objects, 64 programs, 256 threads, 128 handles and 128 mappings per program, 32 threads per program |
| Threads | A thread is a register state and a thread area: the thread record and the kernel ring of the thread. `Thread_Create(entry, stack, parameter)` adds a thread to the caller. The threads of a program share its memory and its handles. A program with no thread stops with code 0 |
| Memory | A memory object is pages with a frame list and a reference count. `Memory_Create` reserves: the budget pays for each page now, and each page gets its zero page frame at its first use, by a page fault or by the kernel. `Memory_Map` maps it in a program. Device memory, thread areas and the first program are contiguous |
| Wait | A thread waits for a time, or on words (the word wait). The kernel has no other wake. For an interrupt, the stop of a held program and the end of another thread, the kernel adds 1 to the event word of each thread of the program, and wakes the threads that wait on that word |
| Word wait | `Word_Wait(address of Word records, count)` and `Word_Wake(address, count)`. The kernel names a word by its page frame, so the word can be in memory that two programs share. One entry can wait on 64 words. `system.Lock` and the wait of a ring are built on it |
| Scheduler | Round-robin over one flat table of threads, with preemption. Each processor takes the next thread that is ready and that no processor runs. A time slice is 10 ms. Idle is `hlt`: a processor that makes a thread ready wakes one idle processor with an interrupt |
| Processors | At most 64. Each processor has a processor record: its kernel stack, its task state with the port bitmap, its segment table, its current thread. One kernel lock: one processor at a time runs kernel code. Each processor has its own timer at 1000 Hz (local APIC); the first processor counts the time. The 16 device lines stay on the 8259 and interrupt the first processor |
| Address translations | Before the kernel frees a memory object, a page table or a thread, each other processor that uses it enters the kernel and forgets it (`processor_sync`) |
| Devices | A Ports object opens a port range in the port bitmap of the program. An Interrupt object counts interrupts and wakes its owner: a line of the 8259, or a message interrupt with a vector of its own. Device memory is a memory object over the registers of a device, mapped with no cache. `Memory_Physical` gives the physical address of a memory object to the holder of the right Physical |
| Faults | A fault in a thread stops its program with a code. The kernel wakes each program that holds its handle |
| Life of a program | A program runs while a handle names it. When its last handle closes, the kernel stops it. Only the root service has no handle |
| Machine | One Machine object with four rights. Inspect: read `System_Report`, `Program_Report` and `Processor_Report` records. Devices: create device handles. Stop: stop the machine. Physical: read the physical address of a memory object. The root service keeps Devices. `monitor` receives Inspect. The console receives Inspect and Stop. A block service receives Physical |

The kernel contains no code for a device, except the timer, the interrupt controller and the serial port of its log. The block service of a virtio disk is a program (`programs/block`).

| `rings` | A display ring; the boot image, to start its `node` programs |
| all others | A display ring only |

The console starts each call host. A call host receives a call ring and a call region only.

A program with only a display ring can draw in its surface and read its own input events. It can do nothing else.

## Choices made during the implementation

The owner did not review these. Each one can change.

1. **Export numbers.** The kernel tool holds an ordered export list per module. The export index is the position in that list. Imports resolve by name at build time only.
2. **Entry instruction.** `syscall`, with the full register state saved per program and a return by `iretq`. The kernel is not preemptible and has one stack.
3. **Give by memory.** `Handle_Give` takes a memory handle to name "the other side of this ring". The kernel has no ring object: a ring is a memory object with a layout that the two programs agree on.
4. **The kernel loads the root service only.** The loader of all other programs is user-space code in `support/system/load.odin`. This closes open question 2 of `ARCHITECTURE.md` in the direction "minimal loader in the kernel, for one program".
5. **Fixed addresses.** A program module is at `0x40_0000`. The stack, the context and the kernel ring have fixed addresses. No random base address.
6. **The compositor is also the desktop shell.** The glossary defines them as two programs. One program holds both roles now.
7. **Grants by program name.** The root service decides the handles of a program from its name, in code. Since step 25 it records the grants that it can revoke, and `revoke` ends one (choices 105 to 113).
8. **Commands of two origins.** The system commands (`programs`, `start`, `shutdown`...) are compiled into the console. `load("math")` loads a module of the boot image: each export becomes a command. The console reads the name, the types and the help of an export from the function table of the module, and calls the export with the call form. `load` checks the hash of the module first.
   **The person chooses the trust.** `load` gives direct calls: the module has the memory and the handles of the console. `isolate` gives isolated calls: the module runs in a call host. The description and the way to type a call are the same.
9. **Font.** Spleen 8x16, BSD 2-Clause, converted from its BDF file by `kerneltool font`.
10. **Types of the description.** `Integer` (64 bits, in a register) and `Text` (the address of a slice record). At most 6 parameters. For a Text result, the caller gives one more argument: the address of a buffer record `{address, capacity}`. The export writes what fits and gives the count of bytes of the full text. In an isolated call the buffer is the free part of the call region. The kernel tool makes the description of each export from the source (choice 26).

11. **Isolated call.** `MODULE_CONTRACT.md` section 4, "The isolated call, as implemented", lists these choices: one call host per module, the argument record in the call region, the status numbers, no time limit (choice 25), a call region of 16 pages, one call at a time per call host.
12. **The caller starts the call host.** The console creates the program with `system.program_start`; the root service takes no part. Any program can create a program: the new program has only the handles that its creator gives.
13. **A program runs while a handle names it.** The kernel stops a program when its last handle closes (stop code `0x200`). Reason: nobody can stop a program that no handle names. A fault gives stop code `0x100` plus the exception number.
14. **The context has no text.** The 256 bytes of text of the context are removed: no program used them, and property 19 forbids them.
15. **One kernel ring per thread.** With one ring per program, a thread that the timer interrupts can get the completion of another thread. Each thread has a thread area that the kernel makes: the thread record (one page), then the kernel ring. `THREAD_AREA_BASE` is the address of the first one; a program has at most 32.
16. **The `gs` register holds the address of the thread record.** `system.call` must find the kernel ring of the thread that runs, on any stack. This amends rule 7 of the module contract: see there.
17. **An event is for all the threads of a program.** An interrupt, the end of a thread and the stop of a held program add 1 to the event word of each thread of the program concerned. A thread that waits on its event word wakes, reads the state, and waits again. The kernel keeps no list of who waits for what event.
18. **A thread ends alone or by its handle.** `Thread_Stop(0)` ends the caller. `Thread_Stop(thread)` ends another thread of the program at any instruction: the caller is responsible for the data that this thread was changing. `Thread_State` and the event at the end of a thread make `system.thread_wait`.
19. **Order in the machine test.** Two programs print in an order that the system does not fix. A `Wait` step with `any_order` does not move the place in the log.
20. **The word wait.** Property 6 proposed "a futex-like wait on a ring counter". `Word_Wait` is a command of the entry that waits: the kernel compares the word and records the wait in one step, so no wake is lost. A word wait ends only by `Word_Wake` on one of its words, by an event if the event word is in the list, or by the deadline. The word is 32 bits on all machines, the size of a ring counter.
21. **The lock is a library.** `system.Lock` is one word with three values (free, held, held with a thread that waits). The kernel has no lock object. A free lock costs one atomic instruction and no kernel entry.
22. **The boot volume is a file that the tool writes.** `tools/kerneltool/volume.odin` writes a FAT32 volume of 64 MiB with the boot program, and the machine gets it as a virtio block device. Before, QEMU made a FAT disk from a folder, on its SATA controller. With KVM, about 1 boot in 10 then stopped in the firmware, in a read of the disk, until an event came to QEMU (measured: 7 of 80 boots with a plain image on SATA, 0 of 160 on virtio). This was the intermittent failure of step 1 of the machine test. A test reads the volume back with a separate reader.
23. **One wait.** The word wait is the one way to wait for something else than a time. `Wake(memory)` and the wake-pending flag are deleted. A queue has two words more, `reader_waits` and `writer_waits`. The reader of a queue sets `reader_waits`, then waits on the `write` counter while the queue is empty. `system.send` writes a record, and enters the kernel to wake the reader only if `reader_waits` is set. `system.receive` does the same for a writer that waits for room. A `system.Wait` is a list of at most 64 words: the compositor waits on the queues of all its clients in one entry. Measured in the machine test: the picture of `rings` and the logs do not change.
24. **The event word.** The thread record has an `events` word. The kernel adds 1 to it for each event of the program (choice 17). A thread reads the word (`system.wait_begin`), reads the state, then waits on the word with the value that it read: an event between the read and the wait ends the wait at once. This replaces the wake-pending flag with the rule of the word wait.
25. **The console runs a line in a second thread.** The first thread reads the keys and draws. The second thread runs each line. The two threads share one `Work` record and wait on its words. During a line, the first thread keeps at most 128 keys, shows the time of the line in a status line, and sets the `cancel` word on Escape. An isolated call waits on the completion queue and on the `cancel` word in one entry. The limit of 2000 ms is deleted: the person decides. Escape does not stop a direct call or a command of the console: that code runs in the console itself, and choice 18 says that a thread stopped from outside can hold a lock.
26. **Descriptions come from the source.** `tools/kerneltool/describe.odin` reads each Odin package with `core:odin/parser`. An export is a procedure with `@(export)` and the calling convention "c". `i64` is an Integer, `^string` is a Text, and a last parameter `^[]u8` is the buffer of a Text result. The description holds the name of the export, the name and the type of each parameter, the result, and the first sentence of the comment as the help. Another type, a missing comment or an export of data is a build error: the tool does not guess. The module table has no description. A function record is 56 bytes. The test reads each module file and compares its descriptions with the source. The kernel exports functions only: its two words that the assembly reads are now in `processor.asm`. The rules are those of the Odin binding; the description in the module file does not depend on Odin.
27. **Rights on handles.** A right is one bit of a 32-bit set in the handle slot. There are 8 rights for 6 kinds of object; the table in `contract/operation/operation.odin` says what each right permits for each kind. `Memory_Map` needs Read, and Write or Execute when the flags ask for them. An operation on another program needs Control on its handle. `Handle_Give` needs Give on the given handle, and Control when the target is a program handle. The copy has the intersection of the rights of the handle and of the mask: a grant never adds a right. `system.program_start` takes grants: a handle and its rights. Each caller names the rights; there is no default "all rights". The boot image handle of the root service has no Write and no Execute. A surface goes to the compositor with Read only. The Machine handle is not split in three kinds: one kind with three rights uses the one mechanism. A thread handle can go to another program with Read only: that program reads the state and cannot stop the thread.
28. **Budgets: no operation creates an object from nothing.** Property 20, line 16, says: "each resource is a handle with a limit; a program divides its limit among its children". A budget is that handle. Three other designs were refused. A limit per program that is only a ceiling does not conserve: the children of a program multiply it. A count per program with no object cannot be given or divided by the handle rules. A budget as a field of the program record makes a second mechanism beside handles. With a budget object, the rights apply (Give, Read, Spend), and the end of a program returns all: `system.program_start` makes a new budget for the program, pays for all that it creates with it, gives the one handle to the program, and closes its own. Two indexes of the context are fixed by the system for each program: `CONTEXT_LOG` (14) and `CONTEXT_BUDGET` (15); `system.log` and `system.memory_create` read them there, so no program has code before its entry. The page tables of a program are paid by the budget that paid for the program. The kernel has no pool of its own after boot: `free pages = sum of the budgets` is the invariant, and the test reads it. The root service chooses each budget by name (`budget_of`).
29. **The log is an object.** The log of the kernel was the last operation that any program could use. It is now a handle with the right Write. The root service gives it with Write; the console and `rings` also receive Give, because they start programs. A program with no log handle logs nothing: `system.log` returns.
30. **Several processors, one kernel lock.** A processor takes the lock at each kernel entry and frees it when it returns to a program or waits for an interrupt. Interrupts are off in the kernel. Property 3 puts the kernel off the hot path: a program enters the kernel to wait, not to work. So the lock is held for a short time, and finer locks add states that nothing needs yet. The kernel counts each acquisition that had to wait (`lock_waits` in `System_Report`), so the cost is a number that `memory()` prints. In one run of the test: 1.7 million kernel entries, 0.6 million waits, most of them during `rings`, where six programs do nothing but wake each other. Review 2 planned one run queue per processor. It is not done: the thread table is flat and the lock covers it, so a queue per processor adds a second structure with no gain while there is one lock.
31. **The processor record.** In the kernel, the `gs` register holds the address of the record of the processor; in a program, it holds the address of the thread record. `swapgs` exchanges the two at each entry and each return. The kernel has no global "current thread". Each processor has its own kernel stack, because a kernel entry starts at the top of the stack and never continues an earlier entry.
32. **`processor_sync`.** The caller holds the kernel lock. It sends an interrupt to a set of processors and waits until each one is in the kernel. Such a processor reloads its page table, then waits for the lock. Two uses. After `Memory_Unmap` and at the stop of a program, no other processor keeps an address translation to memory that returns to the page frames. When a thread on another processor is stopped, the kernel writes 0 in `current` of that processor, then waits: after the answer, that processor does not use the thread, and its entry is not an entry of a thread.
33. **Start of a processor.** The boot program gives the address of the ACPI root record in `Boot_Info`. The kernel reads the processor list (MADT). It copies the start code, less than one page, to the page 0x8000 and starts one processor at a time (INIT, then SIPI). The start code goes from 16 bits to 64 bits with a temporary page table. If the machine has no ACPI tables, or no free low page, the kernel runs with one processor and says it in the log.
34. **The timer is the local APIC.** The kernel measures it against the 8254 once. An idle processor stops its timer, except the first processor. The device lines stay on the 8259: the system has two device interrupts (keyboard, mouse), and a new device class will send its interrupts as messages to a local APIC (MSI), so the kernel needs no I/O APIC code.
35. **One table for the launcher.** `programs/launcher` holds the names and the place of each button. The compositor draws from it and the kernel tool clicks from it: the test step is `Launch` with a name, not a click at a number.
36. **A failure of the check that came sometimes: found.** The flake check of step 11 failed once with "runtime assertion: import" in a unit test of the tool. The tokenizer of the Odin library (`core:odin/tokenizer`) fills its table of keywords at its first use, and its test of "already filled" is outside its lock. The test runner gives each test a thread: two tests that parse Odin source at the same time fill the table twice, and the second stops on an assertion. The tool itself has one thread and is not affected. `tools/kerneltool/describe_test.odin` now fills the table before the threads start.
37. **The boot display is one picture of the records of the kernel.** Owner decision of 2026-11-10: the start of the machine must show a rich, coloured and documented display, with all the facts that help to find a fault, and not a terminal of an old machine. `support/bootscreen/` draws one record (`bootscreen.Data`) at the full resolution of the framebuffer. Each panel names the kernel record that it shows. A record that is all zero is valid: its panel says "not known yet". Three programs draw it: the boot program, the root service, and the program `boot` in a window. The kernel does not draw.
38. **The boot record.** `Inspect` has a new kind, `Boot`, with the record `Boot_Report`: the stages with their times, the memory ranges of the firmware, the firmware, the framebuffer, the sizes, the frequencies of the cycle counter and of the timer. The kernel reads the cycle counter of the processor at the end of each stage. The counter is 0 when the machine starts, so the time before the boot program is the stage "firmware". The kernel measures the frequency of the counter with the wait that already measures the timer. `Program_Report` has `start_time`, and `Processor_Report` has `apic_id`. The kernel also writes each stage on the log ("kernel: boot: ...").
39. **A start that fails keeps the display.** Before, the root service stopped the machine when a start failed. Now it stops the compositor if it runs, draws the boot display with the failure in red, and waits. A person reads the display and stops the machine. The kernel tool builds a second boot image with no compositor, and a second boot volume, and the machine test checks this path (`scenario_fails`).
40. **No pause for the eye.** With a start that succeeds, the boot display is on the screen for about 20 ms under QEMU: the system does not wait so that a person can read it. The program `boot` shows the same display at any time.
41. **The launcher and large windows.** The buttons of the launcher have 4 pixels of padding and 2 of gap (6 and 4 before), for the names (15 now). The compositor moves a new window up and left until the screen shows all of it.
42. **Paging protects the kernel from itself.** Owner decision of 2026-11-10: paging is a design tool. `kernel/paging.odin` gives the kernel half of the addresses three parts. The direct map is data: no address of it is executable. The kernel module has each segment with its own protection, and its code and constants are read-only in the direct map too. The kernel stacks are in their own region. No page of the kernel or of a program is both writable and executable: `Memory_Map` refuses the two flags together.
43. **Guard pages around each kernel stack.** Each processor has a slot of 32 pages of addresses: a guard page, the kernel stack of 16 pages, a guard page, the stack of the double fault of 4 pages, and guard pages to the end. A guard page has no memory. A stack that is full gives a page fault, then a double fault on its own stack, and the kernel reports "the kernel stack of the processor is full". Before, the stack was in the processor record, and a full stack wrote on the record. The first processor leaves the stack of the boot program before it runs the first thread.
44. **The kernel uses the memory of a program in one place.** `user_copy` (in `kernel/processor.asm`) is the one place where the kernel reads or writes at the addresses of a program. If the processor has the guards (SMEP and SMAP), the kernel sets them: any other use, and any jump to the code of a program, is a page fault. The kernel copies the parameters of an operation to its own memory before it uses them. The QEMU machine has `-cpu max` so that the test has the guards.
45. **The kernel reads its own tables.** `Inspect` has a new kind, `Mappings`, with the record `Mapping_Report`: the runs of pages with one protection, the counts, the guard pages. At the start, the kernel reads its half and stops the machine if a page is writable and executable or if a guard page is missing. The program `pages` shows the same record.
46. **Tests of the kernel on itself.** A test that the kernel survives proves nothing about a protection: the test must do the thing that is refused. The boot record has a field `self_test`. The kernel tool builds one boot program for each test (`-define:SELF_TEST=`), and the machine test checks the report of each fault. A normal boot program has the value 0.
47. **The launcher is a menu.** The bar had one button for each program, and 15 names filled it. The bar now has one button, "programs". It opens a menu with one line for each program. A press on a line starts the program, and any press closes the menu. `programs/launcher` still holds the one table of the names and the places: the compositor draws from it, and the machine test clicks from it. The buttons of choices 35 and 41 do not exist any more.
48. **The log is records in channels.** Owner decision of 2026-11-10. A log record (`Log_Record`, 256 bytes) has a number, a time, a program, a thread, a level, a channel and a text. A long text takes several records. The operation `Log` takes a level and a channel; `system.log_in(channel, level, ...)` writes one, and `system.log(...)` writes with no channel and the level Info. The serial port receives the same record as one line: "[program] text", or "[program:channel] text".
49. **The kernel is the one writer of the log.** The first design (in `HANDOFF.md`) had a log service in user space. The implementation has none. The kernel must set the program and the thread of a record, or a program could write a record of another program. With one writer, the log is one memory object with a counter: the last 1023 records. A reader maps it with the right Read and waits on the counter with the word wait. The kernel does no work for a reader: no copy, no operation. A reader that is late knows how many records it lost. A service that keeps or filters records can be a reader later.
50. **Who reads the log.** The root service receives the memory object of the log with Read (`ROOT_LOG_RECORDS`) and gives it to the program `log` (`GRANT_LOG_RECORDS`). No other program has it. The kernel writes its stages in the channel "boot", its page tables in "paging", and a program that stops by a fault in "fault" with the level Warning. The root service writes in "programs", the compositor in "surfaces".
51. **No standard input and no standard output.** Owner decision of 2026-11-10. A program has no ambient stream of bytes: its context has no place "input", "output" or "error". The input of a command is its typed parameters and its output is its typed result (property 19). A flow of data in time is a ring of records. The log is not an output: it is for the person who looks for a fault.
52. **A program that runs serves its own exports.** The file of a program is a module: its exports have descriptions, made from the source as for each module. A service reads the descriptions in its own file (the root service maps the file in the program, read-only, at `isolated.FILE_ADDRESS`) and decodes each argument record with them. The caller reads the same descriptions in the same file. The isolated call has one form for a call host and for a service: `system.export_serve` executes it in the two cases. No contract is specific to services, and no language feature is in the contract: a command record, an argument record and a description.
53. **The root service makes each connection.** A caller asks the root service by the name of the service (`Root_Command.Connect`). The root service creates the call ring and the call region, gives them to the two programs, and keeps none. The service learns of the connection on its service ring (`isolated.Service_Command`). The caller receives a handle to the program with the right Read only: it can learn that the service stopped, and it cannot stop it. The caller does not hold a name or an address of the service: it holds handles (P20). Today the root service gives the grant to serve to `paint` and `life`, and lets each program with a ring to the root service connect; a list of who can call which service is part of the step on principals.
54. **One connection for each caller.** A caller cannot read or write the arguments of another caller: each connection has its own call region. A service has at most 8 callers (`SERVICE_CONNECTION_CAPACITY`). The service ring always keeps room for one Disconnect for each connection: the root service never waits for a service that does not read its ring. A service that gives false counts on its ring harms only itself.
55. **The calls execute in a thread that the service chooses.** `system.service_wait` adds the service ring and each call ring to the wait list of the thread, with the other things that the program waits for. `system.service_run` executes the calls. In `paint` and `life` this is the one thread of the program, between two input events: an export reads and changes the data of the program with no lock. A service that needs parallel calls gives each connection to a thread of its own.
56. **The caller names the file by its hash.** The completion of Connect has the hash of the file of the service. The console finds the file in the boot image by this hash and checks the hash before it reads the descriptions. Each export becomes the command `service.export`. When the service stops, the root service ends the connection, and the next call asks for a new one. If the new program has another file, the console refuses the call: its commands describe the first file.
57. **A ring has a capacity, chosen when it is created.** The memory of a ring is one head page (the counters of the two queues), then the command records, then the completion records: 1 + capacity / 32 pages. The capacity is a power of two from 32 to 65 536. The smallest ring has 2 pages, as before. The capacity is not written in the shared memory: each side computes it from the size of the memory object, that the kernel gives (`system.ring_open`). A side cannot make the other side read outside the ring. A ring does not grow: a queue that grows moves the problem of a slow reader into memory, and needs the kernel on the hot path to map it again in two programs.
58. **A full queue slows the writer to the speed of the reader.** Owner decision of 2026-11-10. The capacity is for the bursts of the writer. Each writer chooses what it does when the queue is full: it waits for room (`wait_room`), it drops the record, or it refuses the request. The writer and the reader change different lines of the processor cache (`ring.Counters`).
59. **One wake for many records.** A writer that waits for room continues when half of the queue is free, or when the reader itself starts to wait: it then writes many records for one kernel entry. `wait_end` sets the `waits` word of a queue, not `wait_records`: a thread that does not wait does not make the other side enter the kernel.
60. **Read the counters before a wait.** `system.wait_spin` reads the words of a wait list about 400 times with no kernel entry, on a machine with more than one processor (the thread record has the count of processors). If a word changes, the thread does not wait, and the other side does not enter the kernel to wake it. A program calls it where the other side answers fast. `wait_end` does not do it alone: it gives the time, and a program reads the time with a kernel entry today. The program `flow` measures the effect: 2 500 times fewer kernel entries with capacity 32.
61. **A terminal is a program, and its input is records.** The package `terminal` is the whole contract: a terminal ring of 4 096 records and a text region of 4 MiB. A record has a kind (`Text`, `Status`, `Clear`), a count of bytes and a style (a tone, flags, a color). No byte of the text has a meaning for the terminal: no escape character, no escape sequence, no control character. The end of a line is a flag of a record. A progress line is a `Status` record with a value and a total: the terminal shows it out of the lines. The kernel knows nothing of this: the two grants are a ring and a memory object.
62. **A record gives a count of bytes, never a place.** The program writes its bytes in the text region, in order, and the record says how many. The terminal keeps its own read place. A program cannot make the terminal read memory that it chooses. The terminal maps the text region read-only, limits each run to 256 bytes, and copies the bytes one time, from the text region to the bytes that it keeps: after that copy, the program cannot change what the terminal shows.
63. **The display does not slow the program.** One thread of the terminal reads the records and keeps the lines. It never draws. The first thread draws at the rate of the screen, and it draws only the cells of the view: 32 rows of 104 cells. It asks the reader for the view with one word; the reader answers between two groups of records. The data has one owner and no lock. The cost of the display does not depend on the count of lines written.
64. **The terminal keeps a fixed amount.** Three areas of a fixed size: 65 536 lines, 262 144 runs, 8 MiB of bytes. The oldest lines leave. Nothing grows while the program runs. When the person holds a view and its lines leave, the view keeps its cells and the window says "older than the lines kept".
65. **One wake for a group of runs.** `terminal.line` writes its runs with `ring.push` and calls `system.wake_reader` one time. `ring.push` and `ring.pop` store the counter with no complete barrier: it costs more than the store. A side calls `ring.complete` before it reads the `waits` word of the other side.
66. **A `waits` word is a word of the wait.** Step 17 had a lost wake: `flow` stopped in 2 test runs of 3. The side that wakes sets the `waits` word of the other side to 0. A late wake, for a record that the thread already read, could set the word of a newer wait to 0: the next record then made no wake. Now `wait_end` gives each `waits` word to the kernel as one more word of the wait, with the value 1. If the other side set it to 0, the kernel does not stop the thread. `wait_end` also wakes the other side of each queue before the thread stops: a reader that was not told of the last records, or a writer that waits for half of the queue.
67. **A surface can have two pictures.** The first picture of the held terminal showed lines of two different views: the compositor read the surface while the terminal drew it. `display.open` with `two_pictures` creates memory for two pictures. `Present` names the picture that is complete; the program draws the other one, after the compositor took the last `Present` (`display.canvas_free`). The compositor checks the size of the memory before it accepts a picture number. A program that draws small changes keeps one picture.
68. **A film is a command of the tool.** `kerneltool film` starts the machine, starts the terminal, sends keys, and asks QEMU for the screen 25 times in one second. `ffmpeg`, from the flake, makes the file. The film is for the development log: it is not a test.
69. **Measured.** In the test machine (4 processors, QEMU with KVM, the other programs of the scenario open): over five runs, `flood` writes 1.7 to 3.0 million lines in one second, 6.8 to 11.9 million records, with 14 to 108 kernel entries for one million records, and the terminal draws 47 to 50 pictures in one second. In the machine of the film (the terminal alone): 3.6 million lines, 14.5 million records, 1 to 6 kernel entries for one million records, 62 pictures in one second.
70. **A shared queue: several writers and several readers, no lock.** `contract/ring/shared.odin`. A ring stays the way between two sides: one writer, one reader, no atomic exchange. A shared queue is for the other case: several threads take work from one place, or give results to one place. Each record has a turn word. A writer takes a count with one compare-and-exchange on `write`, writes the record, then changes the turn word; a reader does the same with `read` (the algorithm of Dmitry Vyukov for a bounded queue). The turn word holds the count minus the place of the record: memory that is all zero is an empty queue (P16). The capacity comes from the size of the memory, as for a ring. A record is the same 64 bytes as in a ring.
71. **A wake for one thread, and three rules that keep the kernel off the path.** A writer adds 1 to the word `written` after each record, and a reader waits on that word. `system.wake_one` wakes one reader only if a reader waits, if no reader reads the word in `wait_spin`, and if the reader of the last wake already runs. A reader that takes a record and sees one more wakes the next reader: the readers that run are as many as the work needs. Without the third rule, a reader that sleeps costs many kernel entries: measured in the test machine, 82 370 and 346 099 kernel entries for one million records with 2 and 3 readers; with the three rules, 6 778 to 13 813 over two runs.
72. **Writers wait for half of the queue.** A writer that finds no room sets `writer_waits` and waits on the word `taken`. A reader wakes all the writers when half of the queue is free: one kernel entry, then many records. This is choice 58 for a shared queue.
73. **A flag that several threads set is not cleared by a thread that leaves the wait.** In a ring, one thread owns each `waits` word, and `wait_end` sets it to 0. For an event and for `writer_waits`, another thread can still wait: the thread that wakes sets the flag to 0 with an exchange, before the wake. A thread that waits gives the flag to the kernel as a word of the wait, as in choice 66: if the flag changes first, the thread does not stop.
74. **An event is two words.** `system.Event` has a count and a flag. `event_wake` adds 1 and wakes all the threads that wait; `wait_event` adds the event to the list of a wait, with the queues and the other words. The zero value is an event that never happened. The condition is in the memory of the program, not in the event: a thread reads the count, reads the condition, then waits while the count is the same. `crowd` starts the threads of each measure with one event, and its queue with a lock uses two events.
75. **The threads of a shared queue trust each other.** A thread that writes wrong numbers cannot make another thread use memory out of the queue: each place is a count and the mask. It can make the other threads lose records. A thread that stops between its compare-and-exchange and its turn word stops the queue at that record. Between programs that do not trust each other, the way is a ring for each pair.
76. **The scenario reads the place of a window in the log.** The compositor writes "surface name WxH at X,Y". The step `Move` of the scenario reads that line and drags the title bar from that place. Before, each drag had fixed coordinates, and a new window in the scenario moved the windows after it: the scenario failed for a reason that was not in the system.

With 2 writers and 2 readers, the shared queue gives 1.1 to 1.8 times the records of the queue with a lock, and enters the kernel 11 to 78 000 times less. More records in one second need more queues, not more threads on one queue (owner decision of step 17).
78. **The time is a page, not an operation.** The kernel has one page, the time page. `program_create` maps it in each program at `TIME_ADDRESS`, read-only and not executable. The record `Time_Record` has one field, the milliseconds since boot; the first processor stores it at each tick of its timer. `system.time()` is one load of 64 bits: the value is always complete, and no sequence count is necessary. The contract is an address and a record: a program in any language reads it. The time was already free to each program (P20): the page gives no new knowledge.
79. **No budget pays for the time page, and no program removes it.** The page is memory of the kernel, taken before the first budget exists: the check "budgets N pages: all the free pages" still holds. `Memory_Unmap` refuses each address at or above the thread areas, and the time page is above them. A second program cannot map another object at this address in a new program: the address is taken at creation.
80. **The kernel entry that gives the time stays.** `system_enter` still returns the time: a thread that leaves a wait has the time with no second read. `system.time_entered` names that path for the measure.
81. **Measured.** In the test machine, four runs: `clock` reads the time 879 to 1 491 million times in one second from the time page, with 0 kernel entries, and 1.9 to 2.4 million times in one second with a kernel entry: 460 to 620 times more. A program that reads the time in a loop (each program that draws, each measure) no longer takes the kernel lock for it.
82. **One module in each role** (owner, 2026-11-10). The system has no difference between a command line program, a library and a dynamic library: the file of `tally` is a program (it has an entry), a service (the program that runs serves its exports), a library (the console maps it in its own memory and calls it directly) and a sandboxed program (a call host runs it). The four uses name one hash. The data of a module belongs to the program that runs it: the four uses give three counts. One rule makes a module good for each role: an export needs nothing from the entry.
83. **A module carries its documentation.** The file has a Documentation table: record 1 has one line that says what the module is, and a text. A record of the Functions table also has the text of its export. The tool takes the text of the module from the comment before the word `package`, and the text of an export from its comment. A package with no such comment does not build. The text has one form (`module.Documentation`): a line is a paragraph, a line that starts with a space stays as it is. The reader breaks the paragraphs: the file does not fix a width. The documentation is in the hashed file: it cannot describe another version of the code.
84. **The manual reads the file and nothing more.** `manual` shows the page of each module of the boot image: it does not load the module and does not start it. The ways to use a module come from two facts of the file: an entry or not, exports or not. The manual is a service with three exports: `show` asks for a page, `about` and `signature` give a description as a text. The console and the manual read the same records: a module has one description, and each program that wants it reads it.
85. **The console removes a module.** `unload` removes the commands of a module that `load` or `isolate` added. A direct load leaves the memory of the console (`system.module_unload` removes each segment). A call host stops when the console closes its handle. A sandbox of the console that has no name is free: the console has 8, and it uses a free one again.
86. **The compositor writes the place of a window that a person puts down**: "compositor: window title moved to X,Y". The step `Move` of the scenario reads the last place of a window, and it fails when the window is not at the new place after the drag. 87. **Two source libraries, and no relative import** (owner, 2026-11-10). The packages that several modules compile in are in two folders, and an import names the library: `contract:ring`, `support:system`. `contract` has what two parties agree on: the kernel operations, the boot record, the module format, the hash, the ring, the isolated call. It uses no kernel operation. `support` has what a program compiles in: `system`, `graphics`, `display`, `terminal`, `bootscreen`, `launcher`, `relay`. The limit is checked by the compiler: the kernel and each package of `contract` compile with the contract library only, so an import of `support:` there is a build error (6 checks). The flake defines the command `kerneltool` with the two libraries.
88. **The root service wires a program and its terminal; the terminal starts nothing.** In step 18 the terminal started `flood`: it held the boot image and a part of the Machine handle, and each program in a terminal had to be a child of the terminal. Now a role of the root service says "this program has a terminal" (`Terminal`). The root service creates the terminal ring and the text region, starts the program with its role, then starts a terminal for it. The terminal receives a surface, the terminal ring, the text region with the right Read, and a handle on the program with the right Read. It has no boot image, no Machine handle, and nothing of the role of the program: the console can stop programs, its terminal cannot. The name of the program, the size of the text and what the window shows are values of the context of the terminal.
89. **Input is records in the completion queue of the terminal ring.** One record for each key that the person presses: the code of the key and its character. No byte stream, no mode "raw" or "cooked", no signal character. The terminal keeps Page Up and Page Down for its view. Each other key goes to the program, and the view returns to the last lines. The terminal never waits for a program: if the program does not read and the queue is full, the key is lost and the log says it one time.
90. **The program owns its line of input; the terminal draws it** (the kind `Edit`). The program sends the text of the line that it changes and the place of the cursor. The terminal shows it after the last line, and a new one replaces the one before. So no record has a place on the screen, the terminal has no line editor and no history, and two programs can edit a line in two ways. The console keeps its history and its keys. While a line runs, the console uses the same record to show the time of the line and the keys that wait.
91. **A program in a terminal has no surface.** The console lost its window, its grid of cells and its drawing code: `programs/console/main.odin` went from 329 lines to 256. It writes runs with a tone (an error has the tone Bad) and the terminal chooses the colors. Its two threads write one ring: a lock orders them, because a queue has one writer.
92. **A terminal draws after a change only.** The reader thread counts the groups of records. The drawer of a terminal that does not show rates waits on that count, on its keys, and looks at the state of its program each 250 ms. A console that waits for the person draws no picture. The terminal of `flood` shows rates: it draws at the rate of the screen.
93. **A program that stops leaves its terminal.** The terminal writes "-- name stopped with code N after N lines --" and keeps the lines: the person can read what a program wrote before a fault. The person closes the window to stop the terminal. A terminal that stops (the person closes its window) stops its program: a program with no terminal can show nothing.
94. **`Program_State` gives the count of kernel entries of the program.** The terminal showed this count with `Machine_Report`, which needs the right Inspect on the Machine handle and gives the facts of all programs. The count is now a third result of `Program_State`, which needs the right Read on one program. The terminal has no Machine handle.
95. **The scenario closes a window with its close button** (step kind `Close`). The tool reads the place and the width of the window in the log and presses the button. Before this step no test pressed a close button.
96. **A Record is bytes with described fields** (`module.Type.Record`). The description of a module has two more tables, Records and Fields: the name and the size of each record, and the name, the offset and the type of each field. A field is an Integer (8 bytes) or a Handle (4 bytes). A record has at most 256 bytes and holds values only: no address. In a direct call the register has the address of the record. In an isolated call the bytes go in the call region, and the receiver copies them to private memory before the call: the caller cannot change a record while the export reads it.
97. **A Record result is one more argument**: the address of the memory of the record, after the parameters. The export has no result type. A result record has no Handle: a callee gives no handle back in this step.
98. **A Handle is lent** (`module.Type.Handle`). The description has the rights that the export needs. In a direct call the register has the handle of the caller. In an isolated call the caller gives a copy to the receiver with these rights only (`system.lend`), and the receiver closes the copy when the export returns (`system.export_serve`). The caller keeps its handle. Measured in the test: an export with a description of Read receives `No_Right` when it maps the object to write, and a handle that an export kept gives `Bad_Handle` at the next call.
99. **The kernel proves where a handle came from** (the operation `Handle_State`, number 23). A receiver reads the number of a lent handle in memory that the caller writes. Without a proof, a caller names a handle that the receiver holds for itself, and the export uses it: a confused deputy. `Handle_Give` with a memory object as the target now records the serial number of that memory object in the new handle. `Handle_State(handle, memory)` says if the handle came through this memory object. The receiver calls the export only if each handle came through the call ring, with each right of the description. A memory object has a serial number because a slot of the table of memory objects serves many objects in time.
100. **The caller checks before it gives.** `system.lend` reads the rights of each handle first: the Give right and the rights of the description. If one handle fails after others went, the caller sends a record of the kind `COMMAND_RELEASE` with the handles that the receiver has, the receiver closes them, and the caller does not send the call. At most 16 handles go with one call.
101. **The source gives the descriptions.** In Odin, a parameter `^Name` is a Record when `Name` is a struct of the package with the layout of the C language; a last parameter `result: ^Name` is a Record result; `system.Lent({.Read, .Write})` is a Handle with its rights, as a parameter or as a field. `Lent` is a struct of 4 bytes: the C convention passes it in a register as the handle. The tool computes the offsets, and the test compares each record of each module file with the source. A contract does not depend on Odin: a module in another language writes the same tables.
102. **A record has no identity but its description.** The console accepts a Record argument when the two descriptions are equal: the same name, size and fields (`module.records_equal`). A record of one module is a record of another module with the same fields. The replacement of an import will use the same comparison.
103. **The console has Record and Handle values.** Each record of a loaded module is a command with the name of the record: `Rectangle(1, 2, 30, 4)` makes a value from one argument for each field. `variable.field` reads a field. The console prints a record with the names of its fields, and a handle with its object and its rights, which it reads from the kernel. `buffer(pages)` makes a memory object, `byte(handle, offset)` reads one byte of it, `release(handle)` closes it. `help()` and `manual` show "Handle(Read, Write)" and the name of a record in a signature; `manual` lists the records of a module with their fields.
104. **`Handle_Give` to a memory object that one other program holds.** Before, the target was the other program that maps the memory object. If no other program maps it yet, the target is now the one other program that holds a handle to it. With two other holders the kernel refuses.
105. **The kernel keeps the origin of each holding** (step 25, `kernel/origin.odin`). A holding is a handle or a mapping. One flat table has one link record of 8 bytes for each holding of each program: 64 programs x 256 holdings, 128 KiB, no allocation. A holding is in the list of the holdings of its origin, with a link in each direction: attach and detach are a constant number of writes.
106. **A close does not hide what a program passed on.** When a handle closes, or a mapping is removed, what came from it comes from its own origin. A program that gives a handle and closes its own does not cut the chain: the first giver can still revoke. Many programs map a memory object and close the handle: the mapping then has the origin of that handle, or none.
107. **The operation `Handle_Revoke`, number 24.** `(handle, program or 0)` ends each holding that came from the handle, in one program (a Program handle with the right Control) or in each program, and what came from those holdings in any program. The handle stays. The mappings of the program that revokes stay: a program does not remove its own memory when it takes back what it gave. The walk has no recursion: the kernel stack does not grow with the length of a chain. The result is the count of holdings that ended.
108. **A program that lost a holding learns it or stops.** Each such program gets an event. A thread that waits on a word of memory that its program lost wakes. A thread that uses the memory stops its program on a page fault: the kernel has no other honest answer to a read of memory that is gone.
109. **`Handle_Give` with the target 0 makes a copy in the same program**, with a part of the rights. It needs no Give right: no other program receives a handle. The copy is the unit of revocation: a program makes one copy for each party that it gives to, and revokes that copy alone. `Handle_State` has one more result: the count of the holdings that came from the handle.
110. **A lent handle is revoked, not trusted.** `system.lend` makes a copy for each handle of a call, gives the receiver a handle that comes from the copy, and `system.lend_end` revokes and closes each copy after the call, on each path. Before, the receiver closed its handle, and a mapping that an export kept stayed. The record kind `COMMAND_RELEASE` of `contract/isolated` is removed: the caller takes back what it gave when it does not send the call.
111. **Measured** (program `origin`, 20 000 cycles, QEMU with KVM, in the test machine with 20 programs open): one lent handle costs 4 kernel entries for the caller and 2000 ns: the copy, the handle of the receiver, the revocation, the close. A copy and its close cost 2 kernel entries and 1100 ns. Before step 25 a lent handle cost the caller 2 kernel entries (the state, the give); it now costs 5 (the state, the copy, the give, the revocation, the close). The cost is for each Handle argument only: a call with no handle has the cost of before.
112. **The root service records the grants that it can revoke.** For each program: the log, the machine, the boot image, the records of the log. Each one is a handle that the root service keeps, and the handle of the program came from it: `Handle_Revoke(handle, program)`. `Root_Command.Grants` reads the two sets (has, lost) and `Root_Command.Revoke` ends one grant. The console has `grants("name")` and `revoke("name", "grant")`. A ring is not in the list: the root service closes its handle of a ring after the start, and the end of a ring is the stop of one of the two programs.
113. **The revocation of the boot image also removes the mapping of the file of a service.** The root service maps the file of a program from the boot image handle. A service that reads its own descriptions after such a revocation stops on a page fault. The root service revokes only what the person asks.
114. **Found by this step: the compositor wrote past its table of windows.** `order` had 16 places and the removal of a window copied from the place after the last one. With 17 programs in the scenario the compositor stopped on a bounds check. The table has 32 places (the root service starts 32 programs at most) and the copy uses slices.
115. **`handle_close` of a Ports handle closes the ports at once** on each processor that has the ports of the program open. Before, the ports stayed open until the next change of program on that processor: a revoked Ports handle must not leave a port open.
116. **A budget has two limits: processor time and log records** (step 26, `kernel/limit.odin`). Pages, programs and threads are things: they move to a new budget and they return. Time does not return. So `processor` is microseconds of processor time in each second, on all the processors together (1 000 000 is one processor), and `log_records` is records in each second. `Budget_Amounts` has 5 fields; `Budget_Create` and `Budget_Read` carry them. No kernel operation was added.
117. **A limit counts in each budget above.** What a thread uses counts in its budget and in each budget that this budget came from. A new budget cannot have a limit above the limit of its origin budget. The first design moved processor time like pages: then the sum of the limits of all the programs could not exceed the processors of the machine, and 30 programs that mostly wait took the processor time of the programs that compute. A limit that counts upward has no such cost, and a program still cannot give more than it has.
118. **The kernel counts processor time with the cycle counter**, from the moment when a processor takes a thread to the moment when it leaves it. The time of the kernel entries of a thread, and of its wait for the kernel lock, is time of the thread. The first idea was the count of timer ticks that `programs()` shows: a thread that waits just before each tick is never counted. That is a hole, so it was not built.
119. **The limit holds in each period of 100 ms.** A thread of a budget that used its part does not run until the next period: the scheduler passes over it, and the timer tick ends its time slice. What a budget used above its part (at most one tick for each processor) it has less in the next period: over many periods the limit is exact. Measured by `limits`: 49 642 of 50 000, 198 746 of 200 000, 602 592 of 600 000 microseconds in one second.
120. **A period has its true length.** The first version counted a period as 100 ticks of 1 ms. Under QEMU a tick can come late; then the threads of a busy budget used more cycles than "100 ms", the budget carried a debt that grew, and the budget of the root service (all the programs) stopped the whole system: the machine test failed two times in three (a program that started did not run). The kernel now measures each period with the cycle counter, and a budget has its part of the true length. Three full runs passed after the change.
121. **Limit 0 is no time.** A budget that is all zero has no processor time and no log record: its threads do not run, and `Log` gives `No_Budget`. Each place that makes a budget names the limits: the root service gives each program one processor for each thread that it can have and 1000 log records in each second; the console gives a call host half a processor and 100 records; `rings` gives each node 20 % and 100 records.
122. **The log limit: the kernel refuses, and counts.** `Log` gives the status `No_Budget` above the limit, and `Budget_Read` gives the count of refused records. The budget of the root service has the limit of the capacity of the log in records: all the programs together cannot write more than one full log in one second.
123. **`thread_start` takes a budget.** The kernel operation `Thread_Create` always took the budget that pays; the library now gives it. A program limits one of its own threads with a budget of its own.
124. **The scenario clicked the console at one fixed place, and a new program moved the windows over it** (the place of a new window depends on the count of windows). Two `Move` steps repair the scenario of this step. The right repair is a way to bring a window to the front by its name; it is the next step.

The button `windows` opens it: one line for each window, with its title, in the order of the client table of the compositor (a line does not move when the focus changes). A `Wait` on "compositor: surface paint" can pass when the file ends in the middle of that line, and the `Move` that follows then reads a part of "at 168,142" as another place: the pointer does not take the title bar, and the test fails with "the window paint is not at 516,408". The two `Move` steps of `paint` are the only ones that directly follow a wait on their own surface line: this agrees with the one failure of step 24, at that step. `log_read` now gives the log up to the last line end, for each wait and each place.

128. **Pages on first use, by default** (paging, second part). `Memory_Create` gives a memory object whose pages have no page frame. The first read or write of a page, by a program or by the kernel, gives it a zero frame. A page that nobody touches costs no frame and no zeroing time: the stack of a program (64 pages) and of a thread (16 pages), the second picture of a surface, the text region of a terminal (4 MiB) and the zero data of a module. The flag `Frames_Now` of `Memory_Create` gives each frame at creation, for a program that must not take a page fault later in a path with a time limit. The default is first use because the rings between programs, the surfaces and the stacks work the same with it: the first write of one side gives the frame, and the other side sees that frame. Measured in the machine test, with a copy of `master` before this step that prints the same count: at the first `memory()`, the desktop used 19 975 pages before and 14 582 after (27 % less, 21 MiB), with 5 518 pages paid and no frame yet; at the end of the test, 24 980 before and 18 376 after (26 % less), with 6 769 reserved pages.
129. **No overcommit: the budget pays at creation, the frame comes at first use.** A reserved page has a free frame at any time: the kernel keeps `free pages = pages of all the budgets + reserved pages`, and the console checks it at the end of the test. So no access to memory fails for lack of memory, and the kernel never has to choose a program to stop. The other design, a budget that pays at the first use, makes a page fault fail when the budget or the machine is empty: a program then stops at a random instruction, with no way to handle it. The cost: a page that nobody touches still takes room in a budget.
130. **The frames of a memory object are not contiguous.** The kernel keeps the frames in a frame list: in the record of the object for at most 4 pages, else in list pages of 512 frames, and a top page above them for more than 512 pages. The budget pays for the list pages (`operation.memory_cost`: 65 pages for an object of 64 pages). `Memory_Create` no longer gives `No_Memory` when the budget can pay, and the free frames have no order to keep. A memory object has at most 1 GiB. Three kinds stay contiguous, with each frame at creation: device memory (the framebuffer, the records of the log, the boot image, the time page), the thread area (the kernel reads the thread record and the kernel ring as one block through the direct map), and the module and the context of the root service (the kernel writes them at boot).
131. **Two places give a page on first use.** A page fault of a program with a page that is not present, in a mapping that permits the access, makes the page present and runs the instruction again. `user_range` makes each page of a range present before the kernel copies to or from a program. Any other page fault of a program stops it, as before: a write to a page without Write, and an address with no mapping. A page fault of the kernel at an address of a program still stops the machine: each path of the kernel that uses memory of a program checks the range with `user_range` first.
132. **Why the page fault path is correct with several processors.** (1) The page fault runs under the kernel lock, as each change of the page tables and of the mappings. (2) `Memory_Map` makes all the page tables of the mapping, and the budget of the program pays for them then: a page fault never takes a table and never fails. (3) A processor does not keep a translation of an entry that is not present. So an entry that becomes present needs no message to the other processors. Two threads that fault on one page at the same time: the second one waits for the lock, finds the entry present, and runs its instruction again. (4) An entry that is present changes only to 0, in `unmap`, and `processor_sync` waits for each processor that uses the table before the frames return: that path is the one of step 25. A thread that faults while another processor removes its mapping waits for the lock, finds no mapping, and its program stops (choice 108). (5) The frame of a page is in the frame list of the memory object, not in a program: a second program that maps the object finds the frame that the first one took, and the two see one page. The frame list changes once for each page, under the lock, and frees with the object.
133. **A new mapping is checked against the mappings, not against the page table.** An entry of a page on first use is 0 until its first use, so it does not show that the address is taken.
134. **What the reports show.** `System_Report` has `reserved_pages` and `first_use_faults`; `Program_Report` has `present_pages`, the mapped pages that have a frame. `memory()` prints the pages in use and the reserved pages. `programs()` prints the present pages of each program, and `monitor` shows them in place of the mapped pages. The program `pages` reads the page table itself, so its half of the program now shows only the pages that the program used.
135. **The machine test waited for "compositor: first frame" before "compositor: surface console".** The system does not fix this order. With pages on first use, the first frame of the compositor takes more time (the frames of its pictures come at the first draw), and the surface of the console came first. The step has `any_order` now (choice 19).

136. **Shared code: the loader prepares a module one time, and each program of the module maps it.** The program that starts programs keeps a table of prepared modules (`system.Prepared_Modules`), by the hash of the module file. A prepared module is one memory object with the segments that do not change after the load: the code, the constants, and the data that is read-only after the rebase. Each program of the module maps these pages with the protection of their segment. It receives a new memory object for each writable segment, with the bytes of the file, rebased for that segment only (`module.rebase_range`): the pages of zeros after them stay pages on first use. The kernel learns nothing of the module format: it maps a memory object with the rights of a handle, as before.
137. **Nobody writes the shared code.** After the preparation, the table keeps a copy of the handle with the rights Read and Execute only, and closes the handle that wrote. A program of the module has a mapping and no handle: a write to its code is a page fault, and the kernel stops it. The program that starts programs cannot write it either.
138. **The starter pays, and a prepared module lives while a program maps it.** The budget of the program that owns the table pays for each prepared module, one time; the budget of each program pays for its writable segments, its stack and its context. Each mapping of a program comes from the handle of the table (choice 105), so `Handle_State` gives the count of programs that map it. At each start, the loader closes each prepared module that no program maps. No new kernel operation is needed.
139. **Three programs keep a table**: the root service (each program of the desktop and each terminal), `rings` (its six `node` programs) and the console (its call hosts, which run the module `host`). `program_start` with no table gives the program its own copy of the module, as before: the program `frames` uses it to measure the difference.

140. **The demonstration: `frames` and `twin`.** `frames` reads its own page table (`Inspect`, kind `Mappings`) to count the pages of a range that have a frame: the answer comes from the tables, not from a counter of the kernel. It starts `twin` from the boot image in three modes (`support:twins`): wait, write a page that `frames` gives, write to its own code. It measures with the cycle counter of the processor and the frequency of the boot record. 142. **A block service is a program with one device** (`programs/block`). The root service holds the two ports of the configuration of the bus (0xCF8, 0xCFC) and no other program has them: a port gives the configuration of each device, so it cannot be given for one device. For a disk, the root service reads the configuration, turns off the line interrupt, sets one message interrupt in the table of the device (MSI-X), gives the device the right to use memory (bus master), and starts a block service with: the device memory of each BAR except the BARs of the table of the interrupts, the message interrupt, 8 pages for the queue, the machine with the right Physical only, and a copy of the configuration in one page. The block service reads the virtio capabilities in the copy and never writes the configuration: it cannot change its interrupt. "PCI discovery by a bus service" was the other way: it is the same code in another program, and the root service would have to give that program the ports and the right Devices. A bus service is the right place when the system finds devices that come and go; the first machine is fixed (P7).
143. **Three additions to the kernel, the smallest that a device service needs.** `Device_Create` has two new kinds. `Memory` makes device memory: the kernel refuses each page that the firmware gave as memory, so the right Devices cannot become a way to map the memory of the kernel or of a program; a mapping of it uses no cache. `Message` gives a message interrupt: one of 16 vectors (64 to 79) on the first processor, with the address and the value that the device writes; the kernel counts it and wakes the owner as for a line. The flag `Contiguous` of `Memory_Create` gives a memory object with each page frame from the creation, in one run of physical memory, and with no frame list; it can give `No_Memory` when the budget can pay (no run is long enough). The operation `Memory_Physical` (number 25) gives the physical address of the first page of such an object, or of device memory, to the holder of the new right Physical on the machine; it refuses any other memory object, whose frames come at first use from anywhere (choice 130). One address names all the pages, so a request to the device is one descriptor for its data, and the block contract has no list of pages. The other way, a physical address for each page of an object made with `Frames_Now`, needs one descriptor for each page of a request and a table of addresses in the block service, for no gain on the first machine: a device that the memory of a program reaches page by page is the case of an IOMMU, a later step. The queue of a block service and each data region are contiguous. Choice 34 planned message interrupts for the next device class; the kernel still has no I/O APIC code.
144. **The machine of the test has three disks at fixed places of the bus** (`support/pci`): the boot volume where QEMU puts it, the data disk at the place 16, the disk of the measures at the place 17. 145. **The block contract is a ring and a data region** (`contract/block`). A request is read, write or flush of blocks of 4096 bytes; values are the first block, the count and a place in the data region. The client gives the data region through the block ring, and the block service proves it with `Handle_State`, as for a lent handle. The device reads and writes the data region of the client: the bytes are never copied. Many requests are in flight; a completion has the tag and a status (Ok, Bad_Command, Out_Of_Range, No_Region, Device_Error, Unsupported). The block service takes a command only when the completion queue has room for it, and the client waits for room in the command queue: a slow client stops its own requests and nothing else. Info gives the size of the disk; Statistics gives the requests, the blocks, the kernel entries of the service and its interrupts, so that the client measures the cost of the two sides. An NVMe driver serves the same contract: nothing in it is virtio.
146. **One block service for one client, started with its client.** The root service starts the block service when it starts a program with the role of a disk, and stops it when the client stops. When a block service stops, the root service turns off the bus master of the device before it frees the memory of the queue: the device does not write in pages that another program receives later. The data region belongs to the client, and the block service has a handle to it while it runs.
147. **A library counts the kernel entries of its program** (`system.kernel_entries`). Each kernel entry of a program goes through `system.enter`, which adds 1 to a word with one atomic instruction. A program measures its own cost with no grant to inspect the machine; the block service gives its count in Statistics.

150. **The format of the data disk: copy on write, two places for the root block, a check in each pointer** (`programs/storage/engine.odin`). Studied before the choice, for the rule "a stop of the machine never shows a part of a change": a journal (ext4, the rollback journal and the WAL of SQLite) writes each change two times and needs a replay at the start; a log-structured disk (LFS, F2FS) needs a cleaner; shadow paging with two meta pages (LMDB) needs neither; ZFS keeps the check of each block in the pointer that names it, so a block that a fault changed is found when it is read. The format takes the last two: blocks 0 and 1 are the two places of the root block (a generation, a check of its own, one entry for each private store); a store has one table block (one entry for each object); an object has one list block (the pointers of its data blocks). A commit writes the changed blocks to free blocks, flushes, writes the root block with the generation plus 1 in the place of the older root, and flushes. A block that the root on the disk names is never written. At the start the service takes the valid root with the highest generation, reads each block that it names and compares each check. A root that the stop of the machine cut has a wrong check: the root before it names blocks that no commit changed. So the disk always has the state of the last commit or of the one before. The old root names the state before the last commit: versions (P9) can grow from it, with a rule that keeps old blocks.

152. **The private store is named by the root service, not by the program.** The command Connect on the service ring has two more fields: the name of the caller as the root service names it (32 bytes), and a grant: an amount and the flag "acts for the person" (`isolated.CALLER_AMOUNT_MASK`, `CALLER_PERSON`). The storage service uses the name as the name of the store and the amount as its limit of blocks. An export takes the name of an object and never the name of a store: a program reaches its own store only (P8). A program that the root service starts again has the same name and finds its data. `system.service_caller` gives the connection of the call that runs. The fields are in the generic contract of a service: any service can know who calls it, and the caller cannot choose.
153. **The storage service is a service with exports**, as `paint` and `tally`: `write`, `read`, `size`, `remove`, `objects`, `stores`. The console calls them with `connect("storage")` and the descriptions of the file; a program calls them with `support/storage`. Each change is one commit on the disk when the call returns: the system has no save action (P9). One thread serves the calls one at a time; a call waits for its block requests, with all the blocks of the commit in flight at the same time.
154. **A service that starts when a program asks for it** (`on_demand` in the root service, P16 "hundreds of background processes"). `connect("storage")` starts the storage service and the block service of the data disk, then connects. The storage service reads the disk before it serves: the call of the first connection waits in its ring.

156. **The person sees each store and revokes a grant.** `storage.stores()` lists each store of the disk with its objects, its blocks, its limit and the count of connections that hold its grant; only a caller with `CALLER_PERSON` sees it. `grants` shows "store", and `revoke(name, "store")` sends the command `Grant` with no amount for each connection of that program to the storage service: the store stays on the disk, the calls of the program give -1, and the program continues. The kernel does not revoke the memory of the connection here, because the program would stop on a page fault at its next call (choice 108); the store is data of the storage service, so the storage service is the place that ends the grant.
157. **A program receives its store when it starts.** A program with the role Store and not Person (`notes`) has its connection to the storage service in its context: the call ring, the call region, the storage service with the right Read, and the file of the storage service mapped read-only at `storage.FILE_ADDRESS` (`support/storage`). The root service starts the storage service first if it does not run. `support/storage` finds each export by its name in that file and encodes the call with its description, as the console does: the program has no copy of the numbers of the exports. A program with no ring to the root service cannot ask for other connections.
158. **The persistent program writes each change** (`programs/notes`): each key of the note is one commit of the object "note", and each step of the count one commit of the object "count". The count is three blocks that each hold the count in each of their 512 numbers: a store that showed a part of one commit with a part of another would show blocks that do not agree. One commit costs 3.1 to 3.2 ms in the test machine: two flushes, and QEMU makes each flush a sync of the file of the disk on the host.
159. **The test of a crash ends QEMU, and the test of a cut write damages the disk.** The tool ends QEMU in the middle of 1000 commits: the next start reads each block with its check and finds the last commit. Ending QEMU loses no write that QEMU already gave to the host, so it cannot cut a block; the tool cuts the root block of the last commit itself (`root_cut`): the next start does not use it and finds the commit before, with each block of it unchanged. ## Gaps

Against the properties and the module contract:

- Property 19 is not complete: the description has no floats, no texts in a record, no record in a record, no list of records, and no handle in a result.
- Imports and replacements: the replacement table binds the loaders of the system: the root service, the console, the call host. A program that maps code by itself can ignore it: the kernel does not check what a program does with its own memory. A module record is what the loader asserts: a program writes and removes the records of its own program, and the kernel does not compare them with the memory. A change of the table does not reach a program that runs: the root service does not start a program again. The loader finds a module only in the boot image, and the person names a module of the table by its name there: the module store does not exist. The check cannot prove that the module of a replacement behaves as the module that it replaces, and no principal signs the table (P9). A module has 8 imports at most, a program 16 modules at most, the table 32 records. A load error holds the first failure only, and one replacement of the path; it does not say which field of two Records differs; a fault report has no stack of calls (see `MODULE_CONTRACT.md`, "The error of a load"). The root service writes the error of a start on the log only: the program that asked the start receives a status.
- A direct call does not limit a Handle to the rights of its description: the module is in the program of the caller and has each handle of that program.
- Revocation: a grant has no end time. The root service cannot revoke one ring (it closes its handle after the start): to end a connection it uses `Disconnect` or stops a program. The person sees the grants of a program in the console only: no window shows the grants of all the programs. A grant that the root service did not make (a handle that one program gave to another) is in the kernel table only: no command shows it.
- A caller can give handles through a call ring and never send the call: the handles fill the 128 places of the table of the receiver until the caller revokes them or stops. A service with several callers needs a limit for each caller.
- `program.has_ports` stays true after the last Ports handle of a program closed: the change of program on a processor then reads the handle table for nothing.
- The console makes a handle only with `buffer`. It cannot make a handle with a part of the rights of another handle.
- A service: the root service has no list of who can call which service. A caller finds the file of a service only in the boot image. A call that never returns stops the one thread of a service such as `paint`: the person stops the call in the console (the console closes the connection) and closes the window of the service.
- A terminal shows one program, and a program has one terminal. A program that has a terminal has no surface. The terminal gives keys only: no pointer, no paste, no size of the view. The person cannot select or copy text. The terminal shows bytes as characters of one cell: no Unicode beyond the font, no wide character. The terminal of a stopped program stays until the person closes its window: no command of the console closes it.
- Only `terminal` has two pictures: the other programs can still show a part of a new picture with a part of the old one.
- The kernel ring of a thread has 32 records. `workers` still takes its tiles from a queue with a lock, not from a shared queue.
- A thread that stops in the middle of a write or a read of a shared queue stops the queue: no thread repairs the record of a thread that is not there.
- The time has a resolution of one millisecond, the tick of the timer. A finer time needs the cycle counter and its frequency in the time page. The time page has no date: the kernel does not read the clock of the machine.
- Limits: the root service gives each program the processor time of all its threads: no program of the desktop is limited below what it can use, and no command changes a limit while a program runs. A thread that another processor stops loses the count of its last part of a time slice (less than 1 ms). The scheduler passes over a thread with no time left each time it looks: with many such threads it reads them for nothing. The log limit is for each second on the tick: 100 records at the change of second can pass as two times the limit.
- An error is a `Status`: one small number for each call. It does not say which parameter, which handle or which limit caused the refusal. The owner asked on 2026-11-10 for errors that are descriptive and informative. The report of a fault has no stack trace.
- The menu of the windows has no keys: the person needs the pointer. Two windows with the same title have two equal lines. The scenario still has clicks and drags at fixed places inside windows that it placed itself.
- `Memory_Unmap` does not free a page table that became empty: the budget of the program pays for it until the program stops.
- Frame pointers are not enforced. An import call goes through a stub that the linker adds.
- The test "a C program calls an Odin module" does not exist.
- The manual shows the modules of the boot image only: the module store does not exist. The documentation has one language. A module in C needs a description file for its documentation: the tool reads Odin sources only.
- The console has no command that ends the connection to a service.
- A thread has no preferred processor: it can change processor at each time slice.
- When each processor runs a thread, a thread that becomes ready waits for the end of a time slice (10 ms at most) or for a thread that waits.
- Shared code: each program that starts programs has its own table of prepared modules: two such programs that start the same module prepare it two times. A module that a program loads in itself (`load` in the console, the module of a call host) is not shared. A prepared module stays after its last program until the next start by the same program. The loader computes the hash of the module file at each start.
- Pages on first use: no page of zeros is shared, so the first read of a page takes a frame, as a write does. A program cannot give back the frames of a part of a memory object that lives. A memory object that is not contiguous has at most 1 GiB.
- The revocation of a mapping walks the frame list of its memory object for each word that a thread of the program waits on. `Program_Report` walks the page tables of the program to count its present pages.
- The 16 pages of the stack of the boot program stay in use after the kernel leaves that stack.
- With a processor that has no SMEP or SMAP, the kernel runs without these two guards. `pages` and the log say so.
- A reader with the grant reads the records of all the programs and all the channels: a grant for one channel does not exist.
- The boot display does not show the records of the log. A long text is cut at 80 characters in the `log` window.
- The boot display needs 976 x 700 pixels. On a smaller screen it is cut.
- A thread that stops with a lock held keeps the lock: the other threads wait with no end.
- The machine test failed one time in four runs of step 24 at the step that moves the window of `paint` ("the window paint is not at 516,408"), and passed at the next run with no change of that code. Step 27 found a cause that explains it (choice 127: the tool read a part of a line of the log) and removed it. The log of the failed run was not kept, so the cause is not proven for that run: if the failure comes again, the cause is another one.
- No network, no document service, no principals, no TPM, no Secure Boot.
- A device reaches all the memory of the machine: the machine has no IOMMU in use, so a block service with a fault can make its device write any page. The block service checks that a request names memory of the client; the device does not check it. Property 5 names the IOMMU as a requirement on real hardware.
- A block service serves one client. The storage service is the one client of the data disk; a second client needs its own disk, or a multiplexer of block rings.
- The places of the disks on the bus are fixed in `support/pci`: the boot record does not give the place of the boot volume.
- The block service uses one queue of the device and one message interrupt. It does not ask the device to send fewer interrupts while many requests are in flight.

- The storage service keeps one version of each object: the root of the last commit and the one before. Property 9 asks for the versions of each object, read at an earlier time, with a retention rule: not done. No snapshot, no clone, no document.
- A store has at most 48 objects, and an object at most 32 blocks (128 KiB); the call region of a connection (64 KiB) is the true limit of one write. The disk has at most 60 stores. The tables of all stores stay in the memory of the storage service.
- The storage service does not encrypt the disk, and the TPM does not seal a key (P17).
- A store is named by the name of the program, as the root service names it: two programs with one name have one store. Principals (P21) are not in the name yet.
- The storage service serves one call at a time; one call waits for each commit (two flushes).
- When a block service stops while a client of it keeps its data region, the device can still finish a request in that region before the root service turns off the bus master.
