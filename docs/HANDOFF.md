# Hand-off: kernel design

Updated 2026-11-10. The first milestone is implemented: the system boots under QEMU to a desktop with a console, a system tool and demos. See `FIRST_MILESTONE.md`.

## What the owner wants

A new kernel that breaks with current designs and keeps the proven ideas of Linux, NT and others.
The starting point is the set of ideas that Jonathan Blow described on stream.
The central theme is data-oriented design. The end goal is a desktop environment and user programs.

The owner wants help to collect separate ideas, develop them, and make them concrete.
Reuse existing software where it fits.

## Current deliverable

The code of the first milestone, with its test under QEMU (`kerneltool test`, `nix flake check`).
`FIRST_MILESTONE.md` describes what the code does, the choices that the owner has not reviewed, and the gaps.
The next step is the owner's review of that file.

`PROPERTIES.md` is the plan of the properties on which the kernel is built. It lists 21 properties, all accepted.

- **Full queues and speed (owner, 2026-11-10)**: the owner accepted all these solutions. A full queue slows the writer to the speed of the reader: a queue does not grow while it is in use. (1) A ring takes its capacity when it is created; the capacity is for the bursts. (2) The reader takes all the records before it wakes the writer, and the writer wakes the reader one time for a batch. (3) On several processors, a side spins for a short time before it waits. (4) More readers, each with its own ring, before a larger queue. (5) A queue for several writers and several readers on the word wait. (6) Large data stays in shared memory; a record names it. (7) The test measures: records in one second through one ring, and kernel entries for one million records. (8) The one kernel lock becomes one lock for each kind of data (scheduler queue of a processor, page frames, handles of a program), as a step with its own measure. Each writer chooses what it does when the queue is full: wait, drop, or refuse.
- **The terminal (owner, 2026-11-10)**: the console is a central entry point: it must be very fast. It must not use the old forms of Unix: no escape characters and no escape sequences. What a program sends to a terminal is typed, structured records (text with typed metadata), through the communication mechanisms of this system. Design the separation at the level of the system: the program that produces, the terminal that shows. Make a demonstration that is fast on purpose: a program that produces a very large amount of information, and a terminal where the display does not slow the throughput. Film it. Make it polished.

The targets are x86-64 first, and ARM64 at best. Use this to make records, handles and the call form simpler: one size for an address, a count and a register value, and no second layout of a record. - **No exceptions in the contracts, and errors that inform (owner, 2026-11-10)**: no contract of the system uses an exception to tell an error: an exception fails at a place that the code does not show, and needs a runtime that unwinds the stack to explain. An error is a value that the call gives back; a fault stops the program. A language that runs on the system can have exceptions inside its own module with its own runtime: the system does not control that and does not serve it; no exception leaves a function of a module (rule 8 of `MODULE_CONTRACT.md`). The owner also rejects error reports in the manner of a global `errno`. Errors must be robust, descriptive and informative. State today: each call gives back its own `Status` (no global state), but a status is one small number: it does not say which parameter, which handle or which limit caused the refusal. That is a gap (recorded in `FIRST_MILESTONE.md`); the design of an error with its detail is a step to plan. Not built yet: a stack trace in the report of a fault. The owner named modules first (2026-11-10): the load of a module, the bind of an import, a replacement, an unload and the execution must each explain a failure. The branch of the imports gives a detail record with a failed load: the stage, the modules and the export by hash and by name, what was expected and what was found, and the replacement that was applied.
- **System errors that diagnose (owner, 2026-11-10)**: the owner names a fault of the NT kernel and of the Linux kernel: a refusal gives a short code ("access denied") with no context, and the person cannot find the cause. In this system an error of the system must be rich and must help to find where the problem comes from. Direction told to the owner, to design as one step after the three branches merge: the status stays the fast answer of a call; when a call fails, the kernel also writes a detail record for the thread, in memory of the thread (no kernel entry to read it, no cost when a call succeeds): the operation, the number of the parameter, the handle and its kind, the right that lacks or the limit and its amount, and for a handle the origin that explains why it has no such right or was revoked (step 25). The loader and the services give the same form of record. A tool turns a record into a sentence. The owner added: this is why a language needs no complex runtime here. The system makes the report, so a module in any language, with no runtime, has complete error reports (the rule that no contract depends on a feature of one language). The record never gives a fact that the caller has no right to see (P20): it explains the handles of the caller, not the objects of other programs.
- **A program that shows the errors (owner, 2026-11-10)**: when the step of the error records is done, a program with a window has one button for each case of error. A press makes the error for real, inside a module, and the window shows the report that the system gave. It is the demonstration of the step, with a scenario in the machine test and a picture. Cases to cover at least: a refused right, a revoked handle, a budget with no pages, a failed load (a missing import, a refused replacement), and a fault inside a module with its stack trace.
- **A program drives its own virtual memory (owner, 2026-11-10, an idea, not yet a decision)**: the owner proposes that programs and modules control their memory organization through paging, and asks if it is dangerous. Answer told to the owner: it agrees with the properties if each action goes through handles. A program acts only on its own address space, or on a program for which it holds a handle with Control, and maps only memory objects that it holds, with the rights of the handle. Today a program already chooses the address, the part of the object and the protection of a mapping (`Memory_Map`). Proposed order, after the branch of the paging merges: (1) change the protection of a mapping and reserve a range of addresses; (2) move pages between memory objects with no copy, and read the "written" marks of pages; (3) a fault on a memory object is an event for a program that serves the object (a pager), with the rule that the kernel never waits for a pager. The dangers and their answers are in the conversation of that date: a pager that never answers, memory that is writable and executable at the same time, physical addresses and large pages, the cost of mapping changes on the other processors, and the memory of the page tables.
- **The interfaces push to data-oriented programs (owner, 2026-11-10)**: the owner recalls the base idea of the system. Good data structures follow the access patterns of the processor: few cache misses, memory read in a line. The system must give developers the tools that make this the easy path, on purpose: the interfaces push in the right direction. Consequences told to the owner, each to plan as a step: (1) each interface of the system gives and takes tables of fixed-size records in memory of the caller, many in one call, never one object for each call and never a list of pointers (the rings, the reports and the descriptions already do so: keep this as a rule for each new contract); (2) the description of a module can name a table of records as a parameter, so that a call between modules passes a table with no copy; (3) memory tools for tables and arenas: reserve a range of addresses, grow in place, take pages back, large pages for large tables; (4) measures: a program reads the counters of the processor for its own threads (cache misses, instructions) through a handle, and a tool shows them, so that a developer sees the cost of a structure with a number.
- **Tools that show memory and execution (owner, 2026-11-10, an addition to the item above)**: the owner agrees that the system does not force a linear layout, and that another layout is sometimes right. The subjects above come in their order, after the work in progress: nothing stops for them. With them, the system gets graphical tools for a developer: an inspection of memory (the pages given to a program, which have a frame, which were written, the mappings and their memory objects) and an inspection of execution (the threads, the processor counters, where the time goes). The programs `pages`, `frames` and `monitor` are the start. Rule that stays (P20): a tool inspects a program only with a handle to it that has the right to inspect.
